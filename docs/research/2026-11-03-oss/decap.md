## Bounded follow-up plan and implementation gate

There is no demonstrated product defect from this comparison. The smallest useful Decap-derived follow-up is a **single optional serialization contract probe**, owned by the parent or a future implementation task:

1. Inspect the full current `tests/import-document.test.mjs` before adding anything. Use the upstream executable-frontmatter fixtures as a checklist: `---js`, `---JS`, `---javascript`, `--- javascript `; source is `packages/decap-cms-core/src/formats/__tests__/frontmatter.spec.js:451–465`. [Pinned fixtures](https://github.com/decaporg/decap-cms/blob/61ceb6e0680bb0362dba6d0cfe346c51e3ca3a58/packages/decap-cms-core/src/formats/__tests__/frontmatter.spec.js#L451-L465).
2. If explicit coverage is absent, probe these as inert input through the target's existing `parseMarkdownDocument`; compare only selected primitive output values and an unmodified sentinel. Under the existing parser, those delimiters do not select any executable engine, so inert Markdown is acceptable. Do not change the parser merely to produce Decap's error message or reject previously valid ordinary Markdown.
3. Include empty body, whitespace-only body, CRLF, missing final newline, and final newline in the same contract probe only if they are not already covered. The invariant is exact body preservation through canonical serialization/parse and title-only patching, with unknown metadata intact. The target's exact Markdown hash pairing makes this more useful than matching Decap's formatting style.
4. Only a failing target reproducer permits a proposed fix. Any fix would be limited to `src/shared/document.mjs` and the relevant existing test file, plus a required caller only if the failure proves it necessary. Review callers with `rg` first. No wholesale formatter replacement or executable-engine compatibility.
5. Parent owns execution. A suitable finite command is a Python `subprocess.run(['node','--test','tests/import-document.test.mjs'], timeout=60, ...)` with bounded output. On a hang, inspect the process/log before rerunning. This research did not execute that probe or assert it passes.

The attachment/path-mapping evidence does **not** establish a target metadata, encoding, or performance bug. In particular, do not add MIME inference, media registries, nested collection configuration, content path migrations, or attachment deletion/replacement rules without a separate user requirement and failing contract case.

## Constraints for any later implementation

- Preserve the last approved UI: no Decap dashboard, fields, status badges, split preview, new buttons, style imports, or changed wording.
- Preserve Markdown plus `editor.json`, legacy Markdown editing, exact body-hash pairing, unknown metadata, browser drafts, and recoverable source errors.
- Preserve runtime content save without app commits, Actions dispatch, app rebuild, or deployment. Candidate refs are the current resumable transaction mechanism, not editorial-review branches.
- Preserve authenticated owner/App/repository checks and CSRF/origin enforcement in `server/auth.mjs:73–148`; Decap browser credentials/OAuth are outside scope.
- Preserve `server/github.mjs:12–25` 15-second request deadline; `server/public-content.mjs:13–20,74–113,164–278` freshness, pending-request coalescing, bounded snapshots/blob memory, immutable commit reads, baseline catalog reuse, and eight-lane changed-file fetches; preserve `server/content.mjs:238–277` six-lane catalog-aware structural validation. Do not copy Decap's `Promise.all(files.map(uploadBlob))` as an unbounded-upload optimization.
- If a performance path is eventually changed, compare the same fixture/input before and after: GitHub call counts, unchanged/sibling body fetch counts, concurrent requests, and retained cache bytes/entries. Existing narrow-read/catalog tests are the first evidence source. No performance path changed here, so no benchmark was needed or run.
