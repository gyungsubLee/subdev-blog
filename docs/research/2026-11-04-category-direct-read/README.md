# 카테고리 조회에서 별도 HEAD 확인을 제거했다

구현·기능 검사·실제 조회·전후 실측을 마쳤다. 별도 HEAD 조회는0회이며, GitHub 데이터 query1회로 카테고리와 저장 기준 커밋을 받는다. 첫 조회는 빨라졌지만 반복 조회 중앙값은 약64ms 늘었다. 성능 동등성은 통과했다고 주장하지 않는다. 현재 상태는 반복 조회 성능 차이에 대한 사용자 결정 대기다.

## 변경 범위와 계약

대상은 `/api/content?kind=categories`다. 공개 조회는 다른 작업에서 수정 중이므로 변경하지 않았다. UI·인증·Origin·CSRF·세션 정책도 유지했다.

기존 경로는 HEAD→커밋→루트 트리→categories.json blob을 읽었다. 불변 캐시가 있으면 HEAD1회만 확인했다. 새 경로는 고정된 GraphQL 읽기 query1회로 categories.json의 실제 데이터를 받는다. 응답의 파일과 기준 커밋은 같은 Commit 객체에서 읽으므로 서로 다른 시점의 데이터가 섞이지 않는다. 기준 커밋은 저장 요청에 사용하며 조회 단계에서 별도로 비교하지 않는다.

파일 모드·형식·2MiB 상한·본문 완전성·오류 상세 비노출 검사를 유지했다. GraphQL의 읽기 POST만 명시적으로 재시도하며 쓰기는 기존 정책을 따른다. 조회 파일을 오래된 세션 커밋에 고정하지 않는다. 매번 현재 파일을 받는다.

저장은 기존 baseCommit·baseRevision 비교와 force:false 갱신을 유지한다. 조회 뒤 원본 브랜치가 바뀌면 저장을409로 거부하는 회귀 검사를 추가했다. 다른 사용자 변경을 덮어쓰는 방식으로 성능을 맞추지 않았다.

GitHub 공식 [Commit.file 문서](https://docs.github.com/en/graphql/reference/commits#object-commit)에서 같은 커밋의 파일 조회 계약을 확인했다.

## 검사

- 변경 전 실패: 카테고리 첫 조회가 데이터 요청1회 대신4회를 수행했다.
- 관련 검사81개와 추가 경계 검사20개가 통과했다. 최종 전체 검사에도 이 검사가 포함된다.
- 최종 `npm run check`:532개 중528개 통과,4개 실패. [전체 로그](check.log)를 보존했다.
- 포트 열기 EPERM2개는 권한 있는 같은 검사에서 통과했다. [런타임3개](runtime.log)는 모두 통과했다.
- 남은 기능 실패2개는 기존 편집기 카테고리 표시와 취소 후 선택 유지 검사다. 이 작업에서 해당 화면과 검사는 수정하지 않았다.
- [HTTP E2E3개](e2e.log), [TypeScript·Vite 빌드](build.log), diff 공백 검사는 통과했다. 빌드의 기존 큰 chunk 경고는 남았다.
- HTTP E2E의 저장·삭제는 격리된 GitHub fixture에서만 수행했다. 실제 사용자 데이터는 조회만 했다.
- 독립 검토는 정확성과 보안을 승인했다. 검토자는 검사를 중복 실행하지 않았고 반복 조회의 성능 차이는 별도로 판단하도록 남겼다.

GraphQL query 오류·401/403·누락 파일·symlink·실행 파일·불완전 텍스트·이전 connection 값·변경한 브랜치·읽기 재시도와 저장 충돌을 검사했다. 테스트의 POST 집계는 읽기 query를 쓰기로 오인하지 않도록 조정했다. fixture는 고정된 읽기 query만 허용한다.

## 실제 GitHub 실측

2026-11-04 KST에 같은 Mac·설정·기존 GitHub CLI 자격 증명으로 이전 함수와 새 함수를 번갈아 실행했다. CLI 사용자 ID가 설정한 소유자와 일치함을 메모리에서 확인했다. 토큰·쿠키는 증거에 저장하지 않았다. 이 비교는 HTTP와 서버 함수 처리 시간을 포함하며 브라우저 렌더링은 제외한다.

콘텐츠 커밋은 양쪽 모두 `ae379ba3db9279e04fd12befb1b757091fbdbcb5`였다. 카테고리48개와 revision이 전부 일치했다. 이전 세션 작업의 콘텐츠 HEAD와는 다르므로 그 숫자를 동일 조건 비교에 섞지 않는다.

- 첫 조회:1,251.16→399.66ms. 외부 요청4→1회.
- 반복4회 중앙값:319.22→382.90ms. 외부 요청은 양쪽 모두1회.
- 반복 조회 차이:+63.68ms, 약20% 증가.
- 변경 전 남은 요청은 작은 HEAD 응답이다. 변경 후 남은 요청은 실제 파일 데이터를 반환하는 GraphQL query다.
- 별도 HEAD·Git 커밋·Git 트리·Git blob API 요청은 변경 후0회다.

[실측 원본](live-results.json)에서 HTTP 헤더와 본문 수신 시간을 분리했다. 서버의 로컬 처리보다 외부 query 응답 시간이 대부분이다. 다른 repository.ref query도 비교했으나 현재 expression query보다 느렸다. [대안 비교](query-diagnostic.json)를 보존했다.

최초 묶음 측정에는 새 방식의 첫 조회2,243ms 표본이 있었다. [초기 결과](live-initial.json)를 보존했다. 본문 수신 시간을 분리한 교차 측정에서는 해당 지연이 재현되지 않았다. 최초 지연의 원인은 확정하지 않았다. 이 표본을 숨기거나 정상 속도로 간주하지 않는다.

## 실제 앱 확인

기존 `dist/native/Second Brain.app`의 소유 서버를 갱신했다. 추가 OAuth 없이 기존1시간 세션을 사용했다. 네이티브 앱과 연결된 Chrome에서 카테고리48개를 읽었다. 화면과 저장 버튼 구성은 변경하지 않았다. [화면](categories.png)과 [앱 접근성 기록](native-ax.txt)을 보존했다.

[앱 요청 기록](native-fetch.jsonl)에서 카테고리 조회는 `/graphql`1회씩이었다. 같은 기록의 `/git/ref/...`는 앱 시작과 Chrome 최초 접속의 공개 조회 경로다. 이 경로는 다른 작업의 소유이며 이번 카테고리 변경과 구분한다. 임시 계측과 조사 탭은 정리했다.

## 성능 결정과 제한

현재 버전은 매 조회에서 실제 최신 파일을 받는다. 이전의 캐시된 파일+작은 HEAD 응답보다 반복 비용이 늘었다. 단순히 query 이름이나 보고 기준을 바꾸어 성능 통과로 처리하지 않았다.

반복 비용까지 줄이려면 데이터 캐시를 재사용하고 갱신 조건을 정해야 한다. 이는 외부 변경을 화면에 반영하는 시점을 바꾸므로 이번 구현에 임의로 추가하지 않았다. 사용자 AGENTS의 성능 보존 정책에 따라 현 측정 차이의 수용 여부를 확인해야 한다.

실제 사용자 콘텐츠 저장·삭제·커밋·푸시·배포는 하지 않았다. 공개 데이터 미게시 안내와 기존 편집기 검사 실패2개는 남았다. context check의 INDEX 크기 초과도 기록을 삭제하지 않고 보존했다.
