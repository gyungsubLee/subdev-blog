# 인증 재검사 — 2026-11-04

새로고침의 로그인 표시와 이번 수정의 복구 결함을 구분했다. Chrome 로그인과 실제 카테고리 조회는 성공했다. 네이티브 앱에서 시작한 새 로그인은 대기에 머물렀다. 이번에는 제품 소스를 추가 수정하지 않았다. UI와 세션1시간 정책도 유지한다.

## 실제 실행 중인 앱

대상은 `dist/native/Second Brain.app`의 실행 파일과 포트5173이다. 조사 도중 PID91551, 서버 PID91581을 확인했다. 이전 검증용 `.tmp/native/auth-recovery` 경로를 먼저 선택하면서 조사용 중복 인스턴스가 생겼다. 이 인스턴스는 포트 충돌로 시작하지 못했으며 창을 닫아 정리했다. 이 조사 중 발생한 충돌을 사용자가 보고한 원인으로 취급하지 않는다.

기존 세션에서 다음 순서를 확인했다.

1. 앱에 콘텐츠 관리·카테고리 관리·글쓰기·로그아웃이 나타났다.
2. 앱 도구 막대의 새로고침을 눌렀다. 직후 로그인 링크가 나타났다.
3. 로그인 링크를 누르지 않고 기다렸다. 관리 메뉴·글쓰기·로그아웃이 돌아왔다.
4. 콘텐츠 관리에 진입했다. 목록과 로컬 초안을 확인했다.
5. 카테고리 관리에 진입했다. 보호된 원본 조회가 끝났고48개 카테고리가 나타났다.
6. 로그아웃했다. 카테고리 화면은 `로그인이 필요합니다`로 바뀌었다.
7. 앱의 로그인 링크를 눌렀다. 앱은 `브라우저 로그인 중`에 머물렀다.

사용자 요청에 따라 현재 연결된 Chrome 탭에서 `/api/auth/github`를 열었다. OAuth 왕복 뒤 관리 메뉴가 나타났다. 같은 Chrome에서 원본 카테고리48개를 읽었다. 이 시점에도 앱은 로그인 대기 상태였다. 따라서 브라우저 로그인 성공과 네이티브 앱의 결과 전달을 하나의 성공으로 보고하지 않는다.

대기 중인 앱의 로컬 상태를 읽었을 때 HTTP202, `state: waiting`, 세션 쿠키 없음이었다. 같은 로그인 URL을 Chrome에서 열자 `Login already started`가 반환됐다. 앱 도구 막대의 새로고침도 대기를 끝내거나 로그인 흐름을 다시 열지 않았다. 홈으로 이동해서 대기 흐름을 취소했다. Chrome의 인증된 카테고리 탭은 사용자가 계속 볼 수 있도록 남겼다.

## 수정 전후 비교

`compare.mjs`는 현재 헤더와 같은 입력을 사용한다. 인증 훅과 네이티브 서버 모듈만 각각 HEAD의 수정 전 코드와 현재 코드로 바꿔 검사한다. 실제 checkout 파일을 교체하지 않고 별도 임시 모듈로 실행한다. 외부 통신은 모의 응답으로 격리했다. 종료 제한은15초이며 실제 종료 코드는0이었다. [결과 JSON](comparison.json)을 함께 확인한다.

### 1. 새로고침 직후의 로그인 표시는 수정 전부터 있었다

두 버전 모두 처음 상태가 `checking`이다. 같은 헤더는 `ready`만 관리 가능 상태로 취급하고 나머지는 로그인 링크로 표시한다. 두 버전 모두 `checking → 로그인 표시 → ready → 관리 메뉴`가 재현됐다.

이는 이번 표본의 실제 세션 해제가 아니다. HttpOnly 쿠키는 JavaScript가 직접 읽지 못한다. 서버 확인 결과를 기다리는 동안 로그인으로 표시하는 분기가 문제다. 권한 확인에는 사용자·설치 권한·저장소·브랜치 조회가 포함되므로 표시가 눈에 보일 만큼 지속한다.

근거: `useManagement.ts:6`, `SiteHeader.tsx:19,65`. 이번 수정 전에도 해당 분기는 같았다.

### 2. 이번에 추가한 창 복귀 확인은 관리 화면을 잠글 수 있다

같은 정상 초기 응답 뒤 창 복귀와 통신 실패를 주입했다. 수정 전은 추가 요청 없이 `ready`를 유지했다. 수정 후는 재확인2회가 실패하고 `blocked`가 됐다. 로그인 링크가 나타나고 관리 메뉴와 글쓰기가 사라졌다. 온라인 이벤트 뒤에는 다시 `ready`로 복구했다.

이것은 이번 수정으로 새로 생긴 상태 전환이다. 초기 로그인 실패와 이미 확인한 세션의 백그라운드 재확인 실패를 같은 `blocked`로 저장하기 때문이다. 통신 실패를 실제 권한 취소와 구분하는 경계가 없다. 실제 서버의 세션 쿠키를 삭제한 결과로 해석하면 안 된다.

근거: `useManagement.ts:30-43,61-67`. 운영체제의 통신 실패를 실제 앱에 주입한 결과가 아니라, 현재 실제 훅과 헤더를 사용한 통제 검사다.

### 3. 중복 방지가 실패한 네이티브 로그인의 재시작도 막는다

수정 전 `/__native/auth/start`는 새 flow를 만들었다. 수정 후에는 유효한 `waiting` flow를 재사용한다. 브라우저가 콜백 전에 닫힌 상황을 비교하면, 수정 전 새 로그인 URL은302로 GitHub에 이동한다. 수정 후는 이미 시작한 flow를 다시 열어410 `Login already started`가 된다.

Swift의 새로고침은 로그인 대기 중 `startBrowserLogin()`을 호출한다. 이번에 추가한 `browserLoginID == nil` guard가 즉시 반환하므로 실제 재시작은 일어나지 않는다. 수정 전에는 기존 흐름을 취소하고 다시 시작했다. 앱의 실제 대기·새로고침 무효 증상과 이 제어 흐름이 일치한다.

근거: `native-auth.mjs:27-39`, `SecondBrain.swift:244-247,286-287`. 두 변경이 단순한 중복 클릭과 사용자의 명시적인 재시도를 구분하지 못한다.

현재 앱에서 처음 누른 로그인이 왜 콜백을 받지 못했는지는 기존 로그에 state별 기록이 없어 확정하지 못했다. Chrome의 성공 콜백이 앱에 연결되지 않은 현상은 확인했지만, 다른 브라우저 쿠키와 콜백 state 불일치 중 어느 것이 최초 원인인지는 추가 계측이 필요하다. 위 재시작 결함을 최초 브라우저 이동 실패의 원인이라고 단정하지 않는다.

## 영향과 남은 검증

실제 읽기 권한 검사는 통과했다. 실제 콘텐츠나 카테고리를 저장·삭제하지 않았다. 변경 권한의 성공 커밋까지 검사한 것은 아니다.1시간 방치 만료와 실제 권한 철회도 검사하지 않았다. 이번 비교는 기능과 상태 전환을 확인하며 성능 동등성을 입증하지 않는다.

공개 콘텐츠의 `GitHub request failed` 안내는 인증된 카테고리 화면에도 남았다. 공개 조회는 관리 인증과 별도 경로다. 이 안내가 나타났다는 이유로 세션 만료나 권한 거부로 판단하면 안 된다.

이전 검증은 정상 로그인 왕복·ACK와 단일 훅 복구 검사에는 통과했다. 그러나 중단된 로그인의 명시적 재시작과 창 복귀 실패 때 실제 관리 화면이 사라지는 영향은 검사하지 않았다. 이번 재검사에서 그 누락을 확인했다. 이전의 정상 왕복 성공만으로 로그인 안정성을 확인했다고 보고한 범위가 넓었다.

다음 수정에서는 명시적인 네이티브 재시작과 중복 시작을 구분해야 한다. 백그라운드 통신 실패도 확정된401·403과 분리해야 한다. 새로고침 표시 문제는 확인 중 상태를 미로그인으로 그리는 분기를 바꾸어야 해결되며, 승인한 구성·색·문구는 유지할 수 있다. 제품 수정은 이번 재검사에서 진행하지 않았다.
