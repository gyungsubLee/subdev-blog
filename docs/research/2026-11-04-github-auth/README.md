# GitHub 인증 조사 — 2026-11-04

인증 후 연결 확인이 한 번 실패하면 화면이 자동 회복하지 않는 문제를 재현했다. 화면은 이 상태도 `로그인`으로 표시한다. 최대 1시간 세션과 자동 갱신 부재도 확인했다. 사용자가 겪은 과거 장애의 단일 원인은 당시 로그가 없어 확정하지 못했다.

소유자: 이 인증 조사 채팅. 상태: 조사 완료, 제품 수정 미실행. 완료 조건은 실제 로그인 왕복 확인, GitHub 요청 실측, 장애 경로 재현과 원인 구분이다. 기존 제품 수정과 실행 중인 서버를 보존했다. 이번 변경은 이 조사 폴더와 작업 기록뿐이다.

## 현재 인증 절차

1. `/api/auth/github`가 state와 PKCE verifier를 만든다. 암호화한 `cms_oauth` 쿠키는 10분 동안 유효하다.
2. GitHub 로그인 뒤 `/api/auth/callback`이 state를 검증하고 코드를 사용자 토큰으로 교환한다.
3. `/user`로 소유자 ID를 확인한다. 서버는 토큰과 CSRF 값을 암호화한 HttpOnly 세션 쿠키를 발급한다.
4. 화면이 `/api/session`을 호출한다. 서버는 사용자, App 설치 권한, 두 저장소, 브랜치와 콘텐츠 구성을 확인한다.
5. 모두 통과해야 `ready`가 된다. 쿠키 만료나 GitHub 401은 `signed_out`, 나머지 확인 실패는 `blocked`가 된다.
6. 네이티브 앱은 브라우저에서 인증한다. 앱이 1초마다 결과를 조회하고 쿠키를 WKWebView에 전달한 뒤 홈을 연다.

브라우저와 WKWebView는 쿠키 저장소가 다르다. 브라우저에서만 로그인해도 앱이 자동 로그인하지는 않는다. 세션은 최대 1시간이며 활동해도 연장하지 않는다. refresh token은 저장하거나 사용하지 않는다.

근거: `app/server/src/handler.mjs:36-114`, `auth.mjs:43-96`, `native-auth.mjs:27-71`, `app/native/SecondBrain.swift:274-347`.

## 실제 로그인과 GitHub 실측

Chrome 전용 탭에서 로그인 버튼을 눌렀다. GitHub 왕복 뒤 글쓰기와 로그아웃 버튼을 확인했다. 기존 네이티브 앱에서도 로그인 버튼을 눌렀다. 브라우저 왕복과 WKWebView 쿠키 전달 뒤 앱의 관리 메뉴가 나타났다. 두 경로 모두 이번 실행에서는 성공했다.

별도 계측은 실행 중인 로컬 서버의 네이티브 로그인 전달 경로를 사용했다. 전달받은 쿠키로 현재 소스의 `handleRequest`를 호출했다. 실제 GitHub 응답을 사용했으며 모의 응답을 넣지 않았다. 측정 시각은 2026-11-04 19:35:56 KST다.

- 별도 프로세스의 첫 세션 확인: `ready`, 5,803ms, GitHub 요청 12회.
- 같은 프로세스의 두 번째 확인: `ready`, 2,255ms, GitHub 요청 7회.
- 같은 프로세스의 세 번째 확인: `ready`, 1,947ms, GitHub 요청 7회.

전체 시간은 서버 처리와 응답 본문 해석을 포함한다. 개별 요청의 `ms`는 fetch가 헤더를 받을 때까지의 시간이다. 로그인 버튼부터 화면 준비까지의 전체 시간으로 해석하면 안 된다. 반복 요청은 기존 불변 파일 캐시를 재사용했다. 권한과 브랜치 확인은 계속 실행한다.

세션을 전달받았을 때 남은 시간은 3,592초였다. 상세 요청과 시간은 [live-results.json](live-results.json)에 저장했다. 토큰·쿠키·CSRF·OAuth 코드는 저장하지 않았다. [live-probe.mjs](live-probe.mjs)는 같은 계측을 다시 실행한다. 이 스크립트는 네이티브 로그인 흐름 하나를 차지하므로 앱에서 로그인 중일 때 실행하지 않는다.

## 재현한 원인과 영향

### 1. 일시적인 연결 실패가 로그인 실패처럼 남는다

`/user` 호출에서 통신 실패를 한 번 주입했다. 서버는 재시도 없이 `HTTP 200`, `state: blocked`, `GitHub connection failed`를 반환했다. 세션 쿠키는 지우지 않았다. 즉, 인증 쿠키가 남아 있어도 관리 기능을 사용할 수 없다.

`useManagement`는 처음 마운트할 때만 상태를 확인한다. 이후 `online`, `focus`, `visibilitychange`를 보내도 요청 횟수는 1회였고 `blocked`가 유지됐다. 직접 `refresh()`를 호출한 뒤에는 `ready`로 회복했다. 현재 제품 호출부에는 이 `refresh()`를 연결한 곳이 없다. 페이지 새로고침은 다시 마운트하므로 확인을 다시 시도한다.

`SiteHeader`는 `checking`, `blocked`, `signed_out` 모두 같은 로그인 링크를 표시한다. 오류 사유도 헤더에 나타나지 않는다. 따라서 확인 대기나 통신 실패를 사용자가 로그아웃으로 해석할 수 있다. 실측에서 확인한 준비 대기 시간과 이 상태 표시가 결합하면 재로그인을 유도한다는 추론이다.

근거: `github.mjs:24-29`, `handler.mjs:102-114`, `useManagement.ts:18-30`, `SiteHeader.tsx:19,65`.

### 2. 1시간 뒤에는 다시 로그인해야 한다

8시간짜리 가짜 GitHub 토큰을 반환해도 세션 만료는 1시간 이하였다. 응답에 refresh token을 넣어도 세션에 보관하지 않았다. 이는 기존 설계서의 의도한 정책이다. 화면은 만료 시점에 상태를 갱신하지 않는다. 따라서 다음 서버 요청에서 401을 받기 전까지 관리 버튼이 남을 수 있다. 이 마지막 화면 시나리오는 소스 분석 결과이며 1시간 방치 실측은 하지 않았다.

근거: `handler.mjs:84-93`, `auth.mjs:60`, `useManagement.ts:18-30`, `docs/superpowers/specs/2026-10-24-github-content-management-design.md:59-60`.

### 3. 중복 로그인이나 오래된 콜백이 정상 세션을 지운다

로그인을 두 번 시작하면 같은 이름의 OAuth 쿠키를 새 값으로 덮어쓴다. 이전 state로 돌아온 콜백은 새 쿠키와 일치하지 않는다. 유효한 기존 세션 쿠키를 함께 보냈어도 응답은 401이었고 세션 삭제 쿠키를 발급했다.

이 경로는 `로그인 중 반복 클릭 → 오래된 탭에서 복귀 → 기존 로그인도 해제`를 설명한다. 독립 모의 요청으로 재현했으며 실제 사용자 세션에 실패 콜백을 보내지는 않았다.

근거: `handler.mjs:47,52-54,95-99`.

### 4. 로그인 코드 교환에는 앱이 정한 제한 시간이 없다

일반 GitHub API 호출에는 15초 제한이 있다. 반면 `/login/oauth/access_token`의 fetch 옵션에는 `signal`이 없었다. 프런트엔드의 `/api/session` 요청도 기본 제한 시간을 지정하지 않는다. 따라서 네트워크나 외부 런타임이 종료할 때까지 기다리는 경로가 있다.

진단 검사는 코드 교환에 abort signal이 없음을 확인했다. 실제 GitHub를 멈추거나 무기한 대기시키는 실험은 하지 않았다. 네이티브 흐름의 10분 만료가 진행 중인 fetch를 중단하지는 않는다.

근거: `handler.mjs:59-72`, `github.mjs:17`, `api.ts:1-2`.

### 5. 네이티브 앱의 결과 전달은 응답 손실에 취약하다

서버는 완료 결과를 한 번 응답하면 흐름을 즉시 삭제한다. 앱이 받은 사실을 확인하는 단계는 없다. 완료 응답을 수신자가 잃었다고 가정한 검사에서 다음 조회는 410이었다. Swift도 한 번의 조회 오류에서 즉시 로그인 실패로 전환한다.

서버의 일회성 소모는 실행으로 확인했다. 실제 macOS 네트워크 손실을 주입하거나 Swift의 오류 화면까지 재현하지는 않았다. 정상 네이티브 왕복은 앞선 실제 검사에서 성공했다.

근거: `native-auth.mjs:55-58`, `SecondBrain.swift:315-344`.
