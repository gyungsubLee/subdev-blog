# 서버가 로그인 인가를 최대1시간 유지한다

구현과 실제 OAuth 왕복 검사를 완료했다. 최초 로그인에서 사용자·소유자·App 설치·정확히 두 저장소·쓰기 권한·브랜치·submodule·콘텐츠 구조를 확인한다. 서버는 성공한 경우에만 암호화한 HttpOnly 세션을 발급한다. 이후 요청에서는 서버가 세션을 로컬 검증한다.

세션은 AES-256-GCM으로 보호한다. 버전·사용자·발급 시각·만료·설정 결속값을 검증한다. 설정 결속값은 Origin·OAuth client ID·소유자·App·설치·저장소와 브랜치를 포함한다. 수명은 토큰 교환 시작부터 최대3,600초이며 읽기로 연장하지 않는다. 구형 세션은 재로그인이 필요하다.

Origin·CSRF 검사를 유지했다. 세션 응답에는 저장소와 브랜치만 넣는다. 콘텐츠 HEAD는 로그인 때 고정하지 않는다. 기존 콘텐츠 조회·쓰기의 최신 HEAD와409 충돌 검사, force:false 갱신, 불변 데이터 캐시는 유지한다. 실제 콘텐츠 요청이401·403을 반환하면 실패를 그대로 전달한다.

## 실행한 검사

- 새 실패 검사: 로그인 설치 확인 누락과 권한 없는 세션 발급을 재현한 뒤 통과했다.
- 유효 세션은 외부 통신 실패를 주입해도 외부 요청0회로 ready다. 반복 요청은 쿠키를 재발급하지 않는다.
- 만료 경계·과도한 수명·미래 발급 시각·구형 쿠키·변조·다른 사용자·설정 변경·Origin·CSRF를 검사했다.
- 콘텐츠 HEAD 변경, 불변 캐시,401·403 보존, 기존 저장 충돌 검사를 실행했다.
- 최종 전체 `npm run check`:528개 중524개 통과,4개 실패. [전체 로그](check.log)를 보존했다.
- 포트 열기 EPERM 실패2개는 같은 소스의 권한 있는 실행에서 통과했다. [런타임3개](runtime.log)는 모두 통과했다.
- 남은 기능 실패2개는 `managed-block-editor.test.mjs`의 카테고리 표시와 취소 후 선택 유지 검사다. 이 작업은 해당 화면과 검사를 수정하지 않았다.
- Python 네이티브 검사2개, Swift arm64 컴파일, ad-hoc 서명 검사, TypeScript·Vite 빌드를 통과했다. 빌드의 큰 chunk 경고는 남았다.
- 최종 독립 검토는 승인이다. 검토자는 검사를 중복 실행하지 않았다.

네이티브 명시적 새로고침은 보호된 restart 헤더로 새 flow를 만든다. 일반 중복 시작은 같은 flow를 사용한다. 새 네이티브 flow는 이전 OAuth 쿠키를 제외해 새 challenge를 발급한다. 이전 challenge 재사용을 실제 handler를 연결한 실패 검사로 재현한 뒤 수정했다. 늦은 callback·쿠키 재전달·ACK 검사는 유지했다.

## 실제 실행과 측정

2026-11-04 KST에 `dist/native/Second Brain.app`과 로컬 포트5173을 사용했다. 앱 소유 서버를 종료하고 최종 소스로 재실행했다. 기존 아이콘·메타데이터·설정은 그대로 두고 새 Swift 실행 파일을 반영했다. 임시 계측은 경로·상태·시간만 기록했다. 토큰·쿠키·OAuth code는 증거 파일에 저장하지 않았다.

실제 앱 로그인→Chrome OAuth→callback 성공→네이티브 쿠키 전달과 ACK→앱 복귀를 두 번 확인했다. 마지막 왕복은 challenge 재사용 수정 뒤 실행했다. 앱과 Chrome 모두 보호된 원본 카테고리48개를 읽었다. 앱 종료와 재실행 뒤에도 관리 메뉴가 나타났다. 실제 사용자 콘텐츠는 저장하거나 삭제하지 않았다.

최초 콜백은 토큰 교환1회와 인가 확인12회를 수행했다. 첫 계측의 토큰 교환 시작부터 마지막 인가 응답까지 약3.2초다. [네이티브 요청 기록](native-fetch.jsonl)을 확인한다. 이 시간은 화면 클릭부터 앱 복귀까지의 전체 지연이 아니다.

같은 Mac·토큰·서버 설정·콘텐츠 HEAD로 이전 handler와 현재 handler를 연속 실행했다. 이전 소스는 [baseline](baseline/handler.mjs)에 보존했다. 스냅샷의 import 경로만 같은 checkout을 가리키도록 바꿨다. 콘텐츠 HEAD는 두 버전 모두 `723231cd3cedd4702d2d77ced9190e63387e852d`였다.

- 매 표본을 cold cache로 측정한 최초 실행: 세션 조회3,267.88/2,182.92/2,108.83ms·각12회 →0.70/0.12/0.10ms·각0회.
- 같은 cold 조건의 카테고리 조회:3,428.74/3,378.41/3,578.59ms·각15회 →1,516.40/1,282.43/1,370.09ms·각4회. 양쪽 모두48개를 반환했다.
- fetcher와 캐시를 유지한 최종 실행의 마지막 표본: 세션1,676.35ms·7회 →0.29ms·0회.
- 같은 최종 실행의 마지막 카테고리 표본:1,610.10ms·7회 →339.79ms·1회. 남은 요청은 최신 콘텐츠 HEAD 조회다.
- 전달한 세션 쿠키는438바이트이며 수신 때 남은 수명은3,596초였다.

[최초 cold 결과](live-results-cold.json)와 [최종 결과](live-results.json)를 분리했다. 최종 계측 코드가 요청 배열을 참조로 저장해 앞선 두 표본의 요청 목록을 마지막 목록으로 덮어썼다. 그 두 목록은 무효이며 시간과 응답은 독립적으로 기록했다. 마지막 표본의 목록은 유효하다. 코드는 배열 복사로 고쳤으며 추가 OAuth는 실행하지 않았다. 이 제한을 결과 JSON에도 명시했다.

실제 시간은 GitHub 응답 변동을 포함한다. 통제된 성능 동등성이나 통계적 보장을 뜻하지 않는다. 검사 fixture에서는 반복 카테고리 조회가 최신 HEAD1회만 요청하는 것도 확인했다.

## 남은 실패와 미확인

공개 조회는 별도로 `Public content is not ready for this commit`을 표시한다. 관리 세션은 ready이고 카테고리 조회는 성공했다. 공개 콘텐츠의 동시 수정과 게시 상태는 이 작업에서 변경하지 않았다.

실제1시간 방치와 실제 GitHub 권한 철회는 검사하지 않았다. 만료는 시간을 전진한 자동 검사로 확인했다. 권한 철회 뒤 세션 확인 자체는 승인한 정책에 따라 만료까지 ready이며, 실제 콘텐츠 요청의 거부는 보존한다.

새로고침 직후 확인 중 상태가 로그인으로 보이는 기존 UI 분기는 유지했다. 최초 네이티브 callback 미수신의 과거 원인도 미확인이다. 이번 정상 왕복을 모든 중단 상황의 안정성 증거로 확대하지 않는다. 네이티브 재시작과 늦은 콜백은 자동 회귀 검사로 확인했다.

커밋·푸시·배포는 하지 않았다. 승인된 UI를 수정하지 않았다. INDEX 크기 초과로 context check가 실패하는 관리 기록 문제는 보존했다.
