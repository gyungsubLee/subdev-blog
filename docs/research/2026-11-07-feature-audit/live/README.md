# 실제 GitHub와 네이티브 검사

실제 GitHub 인증·글과 카테고리 CRUD, 네이티브 직접 조작 검사를 완료했다. 발견한 저장·복구·캐시 오류를 수정하고 재검증했다.
전체 Node 검사 664개가 통과했다. 마지막 표시 조건 수정 뒤에는 영향받는 두 파일의 48개 검사와 빌드도 통과했다.
원본 파일 10,302개를 보존했고 테스트 글·카테고리를 정리했다. 기준일은 2026-11-07 KST다.

## 실행 조건과 범위

- 원본 앱 `dist/native/Second Brain.app`은 다른 프로젝트가 사용하는 5173 포트 때문에 시작 오류를 표시했다.
- 다른 프로젝트를 종료하지 않고 검사 앱 복사본의 포트만 `55173`으로 바꿨다.
- `.env.local`과 원본 앱을 보존했다. `CMS_ORIGIN`은 검사 프로세스의 환경 변수로만 지정했다.
- 현재 웹 빌드, 같은 네이티브 실행 코드, 실제 GitHub OAuth·CSRF·저장 API를 사용했다.
- 실제 CRUD에는 이번에 만든 테스트 글과 카테고리를 사용했다. 정리 중 바뀐 기존 순서 번호 7개는 검사 전 바이트로 복원했다.
- 화면 구성, 문구와 CSS를 유지했다. 편집 콜백을 연결하고, 실패 복구에서 기존 버튼이 보이는 조건만 추가했다.
- 앱 코드의 커밋·푸시·수동 배포 명령은 실행하지 않았다. 콘텐츠의 기존 공개 workflow는 실제로 실행됐다.

추가 파일은 이번 원자 저장의 영수증 6개뿐이다. 원본과 공개 index 모두 글 3,032개·카테고리 48개이며 테스트 항목은 없다.

현재 HEAD와 파일 SHA를 확인한 뒤 그 차이만 검사 전 바이트로 복원했다. GitHub Contents API의 SHA 조건으로 한 번 저장했다.
GUI CRUD 커밋과 API 원본 복원 커밋은 원격 기록에서 구분했다. 카테고리 원본 SHA는 `0a33eeab4d849c87f5f3aed38903fd82af314e0e`로 복귀했다.

## 다운로드 진단

첫 저장 대화상자에서는 `Save`가 비활성이었다. 유효한 파일명과 두 로컬 폴더에서도 같은 상태를 관찰했다.
파일 형식이나 객체 보유 코드를 추측으로 바꾸지 않았다.
원본 코드와 일치하는 정적 복사본 A로 앱을 재시작하자 저장 버튼이 활성화됐고 실제 저장이 성공했다.
Blob URL 해제 코드를 바꾼 B는 실행하지 않았다. A가 통과해 해제가 원인이라는 근거는 얻지 못했다.
최초 비활성 상태의 원인은 미확인이다. 재시작 뒤 통과를 코드 수정으로 해결한 결과처럼 보고하지 않는다.

저장 파일의 SHA-256은 `78b9cb35c1b34280700df157f489afb123167ce5549315a85b9f78403f0f77de`다.
본문은 `Live GitHub CRUD audit. Updated body version v2.`이며 49바이트다.

네이티브 조작 중 창 캡처 API가 `cgWindowNotFound`, `noWindowsAvailable`과 `SCStreamError`를 보고했다.
정확한 앱 경로로 현재 창을 다시 연결하고 실제 상태를 확인했다. 오류 뒤 저장 요청을 중복 실행하지 않았다.
한 수정 클릭은 캡처 오류를 반환했지만, 새 원격 커밋을 조회해 이미 저장됐음을 확인했다.

## 추가 오류와 수정

- 카테고리의 `sources:[]`와 서버의 `sources:[id]` 차이 때문에 저장 뒤에도 미저장 상태가 남았다.
  같은 요청의 확정 원본을 채택한다. 화면 이동 중 받은 확인도 공통 경로에서 복구한다.
  [카테고리 수정 기록](category-save-bug.md)의 대상 검사 26개가 통과했다.
- 새 문서의 영구 캐시, 이전 저장 작업의 overlay와 완료 복구본이 삭제 글을 다시 표시할 수 있었다.
  캐시를 먼저 표시한 뒤 목록을 재검증한다. 서버가 같은 공개 커밋을 증명한 작업만 적용 대상에서 제외한다.
  미저장 편집, 공개 대기 원본과 복구 데이터 원문은 보존한다. [수정 기록](ghost-fix.md)에 경로와 회귀 근거를 남겼다.
- 실패한 저장도 `validating`에 남아 `저장 확인 중`을 표시했다.
  실패한 요청과 현재 요청이 같을 때만 기존 `저장 실패` 상태를 적용한다. 카테고리와 글 편집기에 같은 보호를 적용했다.
  [카테고리 RED](category-failure-status-red.log)는 401·409에서 두 실패를 재현했다. [GREEN](category-failure-status-green.log)은 17개 통과다.
- 실패한 편집본을 다시 열면 일시적인 오류 문구가 사라져 기존 원본 복구 버튼도 숨었다.
  두 화면의 표시 조건에 `failed`를 추가했다. 확인 취소 시 원문을 유지하고, 확인하면 원본을 한 번 읽어 복귀한다.
  [복구 기록](reset-recovery.md)의 두 실패 재현과 48개 통과로 확인했다.

공개 완료의 pending 값, 로그아웃 중 요청, 완료 알림과 Markdown-only 블록 편집도 독립 검토에서 보완했다.
이미지 너비 편집과 undo, 계정 전환 중 타이머 덮기, 오래된 실패 알림을 회귀 검사로 확인했다.
관련 다섯 파일의 검사 91개와 TypeScript 검사가 통과했다. [독립 검토](final-review.md)의 최종 판정은 통과다.

664개 실행 뒤 바꾼 제품 코드는 기존 복구 버튼의 표시 조건 두 줄이다.
이 두 소스와 두 테스트의 변경을 확인하고 영향받는 두 파일 전체를 다시 검사했다. 검사 수를 더해 하나의 실행처럼 보고하지 않는다.
실행 조건·의존성·현재 소스 해시는 [검증 기록](verification.json)에 있다.
서버·네이티브 구현과 의존성은 이번 후속 검사에서 바꾸지 않았다. 앞선 HTTP 7개와 Python 2개의 근거는 그대로 유지한다.

캐시 선표시, 같은 문서의 remount 요청 생략, 본문 지연 로딩과 요청 병합을 유지했다.
새 문서에는 index 재검증 1회를 추가했다. 공개 확인은 같은 작업의 요청을 병합하고 순차 실행하며 전체 기한을 둔다.
101개 블록 입력의 추가 문서 비교는 평균 0.001370ms였다. 실제 장치의 CPU·메모리·렌더링 동등 성능은 측정하지 않았다.

기존 `app/server/src/public-files.mjs`의 마지막 빈 줄과 `content/.github/`를 보존했다.
새 화면이나 문구를 만들지 않았다. 실패 복구에 필요한 기존 버튼만 기존 확인 절차와 함께 표시한다.
실행 로그에는 테스트 러너와 Vite가 출력한 행 끝 공백이 있다. 로그 바이트와 검증 해시를 보존해 커밋에 포함했다.

## 남은 검증 경계

- 최초 macOS 저장 버튼 비활성 원인은 미확인이다. 원본 코드 A의 실제 저장 성공과 구분했다.
- 실제 첨부 업로드·가져오기 전부와 카테고리의 소속 글 일괄 삭제는 이번 실서비스 조작에 포함하지 않았다. 격리 HTTP·회귀 근거를 유지한다.
- 원본 `5173` 포트에서의 시작 성공, 모든 화면 크기의 픽셀 비교와 실제 장치 성능의 동등성은 주장하지 않는다.
- 브라우저 확인창과 하위 세션의 Native 연결 제한은 실제 앱 검사 결과와 구분해 [Native 기록](native-final.md)에 남겼다.
- 기존 청크 크기·중복 `updatedAt`·JSDOM 경고와 context INDEX 크기 제한을 숨기거나 기준을 낮추지 않았다.

준비와 실제 실행을 구분한 문서는 [GitHub 준비](../live-github-preparation.md), [네이티브 준비](../native-live-preparation.md)에 있다.
