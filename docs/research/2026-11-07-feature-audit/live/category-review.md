# 카테고리 저장 수정 독립 검토

명세 판정은 `수정 필요`다. 코드 품질 판정도 `수정 필요`다. 화면을 연 상태의 저장 확인은 고쳤지만, 응답 전에 화면을 떠나면 같은 오류가 남는다.

기준일은 2026-11-07이다. 검토자는 `code-review` 스킬과 STE-KO의 `문서` 표면을 적용했다. 소스, 테스트, 기록만 읽었다. 소스 수정, 테스트, 빌드, GUI, 네트워크 작업은 실행하지 않았다.

## 범위와 기준

이번 검토는 `ManagedCategories.tsx:173`의 확정 카테고리 채택과 테스트 응답, 신규 회귀 검사 두 개를 대상으로 한다. 삭제 응답의 `saved` 허용과 삭제 후 원본 요청은 앞선 승인 범위로 유지했다. 기존 사용자 변경과 다른 담당자의 변경은 건드리지 않았다.

요청한 결과는 서버가 신규 `sources`를 정한 뒤 편집 상태가 남지 않는 것이다. 저장 중 새 편집, 같은 요청의 재시도, 최신 캐시 우선 사용을 보존해야 한다. 기존 UI, 문구, CSS와 불필요한 카테고리 요청을 막는 동작도 유지 대상이다.

## 확인한 장점

- `ManagedCategories.tsx:175`는 현재 `requestId`가 확인 대상과 같을 때만 카테고리를 교체한다. 새 편집에는 새 `requestId`가 생기므로 오래된 응답이 그 편집을 바꾸지 않는다.
- `ManagedCategories.tsx:170`은 원본 캐시를 먼저 사용한다. `background-sync.mjs:93`의 `syncVersion` 보호를 유지하므로 오래된 응답의 카테고리를 직접 적용하지 않는다.
- `managed-categories.test.mjs:54`의 응답은 서버 `content.mjs:711`과 같이 기존 필드를 유지하고 신규 `sources:[id]`를 만든다. 이전 응답이 생략했던 차이를 검사한다.
- JSX, CSS, 제품 문구를 바꾸지 않았다. 일반 저장에 카테고리 요청을 추가하지 않았다. 신규 단언은 문자열, 불리언과 작은 배열만 비교한다.

## 발견 사항

### Important — P2: 화면 밖에서 받은 저장 확인에는 정규화가 빠진다

위치는 `app/web/src/features/content-management/ManagedCategories.tsx:173`이다. 카테고리 정규화가 컴포넌트의 이벤트 처리기에만 있다.

신규 카테고리를 저장한 뒤 응답 전에 다른 화면으로 이동하면 이 컴포넌트는 사라진다. `BlogView.tsx:165`가 카테고리 화면에서만 컴포넌트를 렌더링한다. `ManagedCategories.tsx:200`은 컴포넌트가 사라질 때 확인 이벤트 구독을 해제한다. 반면 `useManagement.ts:81`의 동기화는 세션을 따라 계속 실행한다.

이때 `background-sync.mjs:94`는 원본 캐시에 서버 카테고리를 보관한다. 124행은 편집본에 버전, 커밋과 공개 상태만 기록하고 `categories`는 교체하지 않는다. 따라서 편집본의 신규 카테고리에는 `sources:[]`가 남는다.

사용자가 다시 카테고리 화면을 열면 `ManagedCategories.tsx:58`이 그 편집본을 그대로 복원한다. `saved` 상태에서는 330행의 비교가 서버 `sources:[id]`와 다르다고 판단한다. 저장 버튼이 켜지고 삭제 버튼이 꺼지는 증상이 다시 나타난다. 이는 같은 저장 오류의 미수정 경로다.

공유 확인 기록을 쓰는 경로에서 같은 `clientRequestId`의 카테고리 편집본도 정규화해야 한다. 기존 버전 보호와 새 편집 보존 조건을 유지해야 한다. 응답 전에 컴포넌트를 해제하고, 응답 후 다시 여는 회귀 검사를 추가해야 한다.

`tests/web/managed-categories.test.mjs:140`의 재진입 검사는 응답 후에 컴포넌트를 다시 연다. 따라서 위 경로를 검사하지 않는다. 이 발견은 실행 재현이 아닌 소스 흐름에 근거한다.

Critical 발견 사항과 Minor 발견 사항은 없다.

## 검사 근거와 한계

- [RED 기록](category-save-red.log)은 신규 저장 검사 한 개가 저장 버튼의 `disabled` 단언에서 실패했음을 보여 준다.
- [GREEN 기록](category-save-green.log)은 관련 검사 15개가 종료 코드 `0`으로 끝났음을 보여 준다. 기록된 실행 시간은 32.73초다.
- 검토 시 두 파일의 SHA-256은 [오류 기록](category-save-bug.md)의 GREEN 직후 값과 같았다. 제공된 검사 근거가 현재 검토 소스와 연결된다.
- 상위 담당자는 빌드 통과를 전달했다. 검토자는 빌드를 다시 실행하지 않았다.
- 새 편집 보존, 같은 요청의 재시도, 추가 카테고리 요청 방지는 제공된 테스트와 코드로 확인했다. 화면을 떠난 동안의 확인과 실제 여러 탭의 동시 편집은 실행하지 않았다.
- 정적 diff에서 UI 변경은 없다. 브라우저에서 화면을 비교하지 않았으며 실행 시간, 메모리와 렌더링 성능의 동등성도 측정하지 않았다.

## 판단을 보류한 범위

- 앞선 삭제 수정의 재승인은 보류했다. 상위 담당자가 이미 승인하고 검사한 범위이며 이번 추가분에 속하지 않는다.
- 기존 `background-sync.mjs`의 중복 `updatedAt` 경고는 범위 밖이다. 이번 변경이 만들지 않았으며 GREEN 결과를 막지 않았다.
- 여러 탭이 서로 다른 미저장 편집을 만드는 기존 동작 전체는 재설계하지 않는다. 이번 변경의 캐시 선택이 기존 버전 보호를 유지하는지만 검토했다.

병합 준비 판정은 `수정 후 가능`이다. 상위 담당자는 화면을 떠난 동안에도 카테고리 편집본을 정규화한 뒤 해당 회귀 검사를 실행해야 한다.
