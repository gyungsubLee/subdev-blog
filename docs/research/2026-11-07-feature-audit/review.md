# 독립 코드 검토

**요구사항 판정: 수정 필요. 코드 품질 판정: 수정 필요.**
카테고리 삭제의 실제 성공 응답을 웹이 실패로 분류한다. 따라서 새 원본을 읽는 수정이 정상 서버 응답에서 실행되지 않는다.
첨부 업로드와 날짜 검사는 검토 범위에서 추가 결함을 찾지 못했다.

기준일은 2026-11-07이다. 검토자는 제품 코드를 수정하지 않았으며 테스트와 브라우저를 실행하지 않았다.
통합 검사의 실행 소유자는 상위 에이전트다.

## 검토 범위

- `docs/superpowers/plans/2026-11-07-feature-audit.md`
- `.tmp/feature-audit/review.patch`의 제품 코드와 회귀 검사 전체
- `docs/research/2026-11-07-feature-audit/web.md`
- `docs/research/2026-11-07-feature-audit/content-native.md`
- 변경한 함수의 호출부, 저장 큐의 확인 경로와 서버의 응답 생성 코드

기존 `app/server/src/public-files.mjs`의 빈 줄과 `content` 변경은 검토 대상에서 제외했다.
현재 화면, 저장 충돌 검사, 캐시, 지연 로딩과 요청 병합을 유지하는 조건으로 검토했다.

## 발견한 결함

### P1 — 실제 삭제 성공 상태인 `saved`도 원본 갱신으로 이어져야 한다

위치: `app/web/src/features/content-management/ManagedCategories.tsx:237`과 새 갱신 경로 `:242`.
회귀 검사의 응답 위치: `tests/web/managed-categories.test.mjs:59`.

`deleteCategory`는 `published`, `superseded`, `unchanged`만 성공으로 받는다.
그러나 서버의 `acceptedCandidate`는 최초 원본 저장에 `saved`를 반환한다. 근거는 `app/server/src/content.mjs:220`이다.
카테고리 삭제는 단일 작업 요청이다. `withReceipt`는 단일 작업의 상태를 바꾸지 않는다. 근거는 같은 파일 `:644`다.
같은 삭제 요청을 다시 보내도 현재 커밋이 삭제 커밋이면 `saved`를 반환한다. 재시도 경로는 `:664`에 있다.

기존 서버 검사도 이 계약을 명시한다.
`tests/server/github-content.test.mjs`의 `category move deletes only the category and moves original documents to unclassified atomically`는 `saved.state === 'saved'`를 확인한다.
이 검사를 이번 검토에서 다시 실행하지는 않았다.

최소 재현 조건은 다음과 같다.

1. 카테고리 화면에서 삭제를 확정한다.
2. 서버가 삭제를 저장하고 `200`과 `{state:'saved', candidateCommit, contentCommit, deletedPostIds}`를 반환한다.
3. 웹은 `:237`에서 실패 분기로 들어가 오류를 표시한다.
4. 웹은 새 카테고리를 조회하지 않는다. 삭제한 행, 이전 버전과 삭제 요청을 유지한다.
5. 같은 요청을 재시도해도 다른 저장이 없으면 같은 오류가 반복된다.

새 회귀 검사는 삭제 응답을 `published`로 고정한다. 이 응답 때문에 실제 성공 경로를 검증하지 못한다.
최소 수정은 `saved`를 원본 저장 확인으로 인정하는 것이다. 공개 게시 완료와 원본 저장 완료의 기존 구분은 유지해야 한다.
삭제 fixture도 실제 `saved` 응답을 사용해야 한다. 이어서 새 버전 저장과 원본 조회 실패 후 재시도를 검사해야 한다.

이 상태 분류 오류는 수정 전에도 존재했다. 이번 조사에서 발견한 기존 결함이며 새 갱신 코드가 만든 회귀는 아니다.
다만 이번 수정의 완료 조건인 삭제 후 후속 저장을 막으므로 완료 전에 수정해야 한다.

## 영역별 판단

### 카테고리의 초안과 재시도

새 원본 조회 자체는 분류와 버전을 함께 바꾼다. 이전 `baseCommit`과 `baseRevision`을 다시 쓰는 원인은 이 경로에서 해소한다.
`deleteError`는 저장하지 않은 수정이 있으면 삭제를 막는다. `saving`과 `savingRef`는 삭제 도중 편집과 중복 요청을 막는다.
원본 조회가 실패하면 `requestKey`를 지우지 않는다. 같은 삭제 요청을 다시 확인하는 계약도 유지했다.
위 P1 때문에 실제 `saved` 응답에서는 이 동작에 도달하지 못한다.

### 첨부 업로드와 전송 중인 저장

새 조건은 기존 편집기의 `busy` 조건과 백그라운드 게시 여부를 일치시킨다.
이름 예약은 요청 전에 실행한다. 실패하면 예약을 해제하고, 성공하면 현재 초안의 첨부 목록에 합친다.
`publish`는 전송 전에 초안을 복제한다. 새 첨부가 이미 전송한 작업을 바꾸지 않는다.
확인 응답은 현재 초안의 버전을 갱신한다. 후속 첨부를 포함한 현재 초안 필드는 유지한다.
새 경쟁 검사는 이전 작업의 첨부 목록, 확인 뒤의 첨부 보존과 다음 저장의 버전을 확인한다.

### 달력 날짜와 시간대 offset

기존 정규식과 `Date.parse` 검사를 유지했다. 추가 검사는 시간대 변환 전 날짜의 일자를 확인한다.
이 방식은 월말 초과를 거부하면서 정상 offset 문자열을 바꾸지 않는다.
새 검사는 두 날짜 필드의 잘못된 윤일과 월말을 포함한다. 정상 윤일과 양수·음수 offset도 확인한다.
`validateKnownFields`를 공유하는 전체 문서, 기존 형식, 수정본과 직렬화 경로를 읽었다.

## 보존 조건과 검증 한계

- 제품 JSX, CSS, 문구와 새 화면은 바꾸지 않았다. 실제 화면 비교는 상위 담당자의 Chrome 결과가 필요하다.
- 일반 저장의 원본 조회 경로는 바꾸지 않았다. 삭제 후 `refresh=1` 조회 한 번만 추가한다.
- 첨부 이름 예약, 게시 중 첨부 보호와 저장 요청의 복제를 유지했다.
- 공개 캐시, 편집기의 지연 로딩, 세션 요청 병합과 저장 충돌 검사 코드는 바꾸지 않았다.
- 날짜 비교는 날짜 필드마다 추가 연산을 한다. 성능 수치는 `content-native.md`의 담당자 측정값이며 독립 재측정값은 아니다.
- 신규 검사는 DOM 객체를 assertion 진단 값으로 전달하지 않는다. 지연한 응답은 `finally`에서 해제한다.

검토자는 제공한 실행 보고를 읽고 코드와 대조했다. 보고된 테스트 통과를 독립 실행 결과로 주장하지 않는다.
다음 행동은 P1을 수정하고 실제 `saved` 응답을 쓰는 회귀 검사를 실행하는 것이다.

## 수정 후 재검토 — 최종 판정

**최종 요구사항 판정: 통과. 최종 코드 품질 판정: 통과.**
앞의 초기 판정과 P1 기록은 발견 근거로 보존한다. 현재 변경에서는 P1을 해소했으며 새 결함을 찾지 못했다.
재검토 범위는 `.tmp/feature-audit/review-final.patch`의 P1 수정과 새 HTTP 검사다.

`ManagedCategories.tsx:237`은 이제 `saved`를 원본 저장 확인으로 받는다.
삭제 뒤 원본 조회, 현재 버전 갱신과 삭제 요청 정리가 실제 서버 응답에서도 실행된다.
`setPublication(next)`는 상태를 `published`로 바꾸지 않는다. 기존 `PublishStatus`는 `saved`를 `원본 저장 완료`로 표시한다.
공개 게시 확인은 기존 `candidateCommit` 조회 경로를 따른다. 원본 저장과 공개 게시의 구분을 유지했다.

삭제 fixture는 `saved`와 `candidateCommit`을 반환한다.
후속 저장 회귀는 `원본 저장 완료` 문구와 새 `baseCommit`, 새 `baseRevision`을 함께 확인한다.
원본 조회 실패 회귀는 같은 삭제 요청 재시도와 최신 원본 보관을 확인한다.

`tests/e2e/category-crud-http.test.mjs`도 읽었다.
이 검사는 실제 서버 핸들러와 GitHub 프로토콜 fixture를 연결한다. 웹 UI를 실행하는 검사는 아니다.
분류 생성·이름 변경·상위 분류 변경, 하위 분류가 있는 부모 보호, 글 이동과 전체 삭제를 검사한다.
실제 `saved` 응답, 이전 버전 거부, 새 버전 저장, 동일 삭제 재시도와 공개 결과도 확인한다.
요청에는 제한 시간이 있다. 종료 정리는 `t.after`에 등록하며 assertion은 문자열·숫자·작은 배열을 비교한다.

다음 실행 로그를 직접 읽었다. 실행자는 각 검사의 기존 소유자이며 검토자는 재실행하지 않았다.

- `/private/tmp/subdev-web-saved-red.log`: 수정 전 두 회귀가 모두 실패했다. 성공 문구 누락과 원본 조회 미도달을 확인했다.
- `/private/tmp/subdev-web-saved-green.log`: 수정 후 카테고리 검사 13개가 통과했다. 실패·취소·건너뜀은 0개다.
- `/private/tmp/subdev-audit-e2e-final.log`: 새 카테고리 생명주기 검사를 포함한 HTTP 검사 7개가 통과했다. 실패·취소·건너뜀은 0개다.

전체 테스트, 브라우저 화면과 성능 측정은 이번 재검토에서 실행하지 않았다.
다음 행동은 상위 담당자가 전체 검증 결과와 이 최종 판정을 종합 보고서에 연결하는 것이다.
