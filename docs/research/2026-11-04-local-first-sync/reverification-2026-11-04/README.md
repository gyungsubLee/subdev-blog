# 이관 작업 재검증

이관 작업에서 확인 조건 두 곳이 빠진 것을 재현하고 보완했다. 일반 조회·저장·복구·정리 경로는 다시 통과했다. 대용량 큐의 메모리 안전은 확정하지 않았다.

## 발견한 문제와 보완

**창 간 완료 알림:** 실패로 보관한 묶음도 기록이 존재하면 `confirmed`로 통지했다. 원격 확인 후 기기 반영이 끝나지 않은 묶음도 같은 문제가 있었다. 늦은 알림을 재현하자 두 경우 모두 완료 이벤트가 나왔다. [재현 결과](red.log)를 보존했다.

[background-sync.mjs](../../../../app/web/src/features/content-management/background-sync.mjs:230)는 이제 `state === 'confirmed'`와 `applied === true`를 함께 확인한다. 실제 Chrome의 두 탭에서도 실패 알림이 `failed`로 전달됐고 완료 결과는 없었다. 편집 화면 오류는 발생하지 않았다.

**커밋 불일치 기록 정리:** 정리 함수는 요청 ID·본문 해시와 커밋 형식은 확인했지만, 보관한 결과의 커밋과 같은지는 확인하지 않았다. 확인 응답의 커밋만 바꾼 기록도 삭제했다. 이는 손상한 기록을 주입한 검사이며 실제 사용자 기록 삭제를 관찰한 것은 아니다.

[sync-core.mjs](../../../../app/web/src/features/content-management/sync-core.mjs:250)는 이제 확인 응답과 보관 결과의 커밋이 같아야 삭제한다. 실제 Worker 두 개를 동시에 실행해 유효 기록 하나만 삭제했다. 실패·기기 미적용·해시 불일치·커밋 불일치 기록 네 개는 남았다. 다른 Worker는 잠금 때문에 건너뛰었다.

제품 변경은 위 확인 조건 두 곳이다. 회귀 검사 두 개와 E2E 관찰 코드를 추가했다. 승인한 화면·저장 충돌·세션·CSRF·5초 정책·재시도 간격은 변경하지 않았다. 기존 사용자와 다른 작업의 수정은 보존했다.

## 검사 결과

- 재검증 시작 시 기존 명세의 핵심 파일 17개는 모두 같았다. 전체 의존 파일과 실행 산출물의 연결이 부족해 현재 상태에서 전체 검사를 다시 실행했다.
- 보완 전 전체 검사: 574개 중 572개 통과했다. 추가 회귀 검사 두 개는 예상한 정책 위반으로 실패했다.
- 보완 후 전체 검사: **576개 중 574개 통과했다.** 기존 실패 두 개는 아래에 남겼다.
- 최종 관련 검사: **13개 모두 통과했다.** 테스트 시간 초과 시 대기와 자원 정리도 끝나도록 연결했다.
- HTTP E2E와 최종 빌드는 통과했다. 기존 큰 번들 경고와 `updatedAt` 중복 키 경고는 남았다.
- `git diff --check`를 통과했다. 커밋·푸시·배포는 하지 않았다. 실제 사용자 콘텐츠를 대상으로 쓴 검사는 없으며 쓰기 E2E는 임시 저장소에서 실행했다.

남은 전체 검사 실패:

1. `category action precedes preview and shows the assigned name or empty label`
2. `tags, category cancellation and reader controls preserve local-only drafts`

[전체 결과](full-check-after-fix.log), [최종 관련 검사](green-final.log), [빌드 결과](build-after-fix-result.json), [산출물 해시](verification.json)를 보존했다. 전체 검사 뒤 추가한 변경은 테스트 대기 취소 처리와 E2E 관찰 코드다. 해당 테스트는 최종 관련 검사에서 다시 실행했다. 제품 코드와 빌드는 전체 검사 이후 바꾸지 않았다.

## 실제 동작과 실측

| 항목 | 비교 기준 | 현재 결과 |
|---|---:|---:|
| 실제 GitHub 카테고리 조회, 5회 중앙값 | 직접 조회 499.82ms | 캐시 0.22ms |
| 위 조회의 GitHub 요청 | 매번 1회 | 0회 |
| Chrome 반복 화면, 3회 중앙값 | 캐시 미적용 476.4ms | 캐시 우선 122.3ms |
| 카테고리와 글 2개 HTTP 전송 | 개별 1,148.76ms | 벌크 373.42ms |
| 위 전송의 앱 요청 / 원본 커밋 | 3 / 3 | 1 / 1 |

GitHub 조회는 같은 소유자와 같은 원본 커밋에서 카테고리 48개를 읽었다. 내용 해시도 같았다. 화면과 HTTP 전송은 같은 임시 저장소에 API 지연 350ms를 적용한 결과다. 전송 시간에는 디바운스 대기 5초를 포함하지 않는다.

Chrome의 캐시 표시 표본은 122.3/89.9/333.9ms였다. 세 번 모두 목록 다운로드가 없었다. 이 값은 임시 글 하나의 결과이며 실제 글 전체의 렌더링 시간으로 해석하지 않는다. [브라우저 기준](browser-before.json), [현재 브라우저](browser-after.json), [실제 GitHub](live-category.json), [HTTP 저장](http-bulk.json)을 확인한다.

저장 직후 5초 안에 새로고침했다. 기기 편집 내용을 유지했고 원격 요청 하나·원본 커밋 하나로 저장을 완료했다. 원본 글 다운로드는 최초 한 번이었다. 이후 캐시에서 다시 편집기를 열었다. [복구 화면](recovered-save.png)을 보존했다.

실제 IndexedDB·Worker·BroadcastChannel을 사용한 경계 검사도 통과했다. 정리는 11.1ms에 유효 기록 하나만 삭제했다. 그동안 화면 프레임 두 개를 관찰했다. 기존의 18초 지연은 이번 표본에서 재현하지 못했다. 원인을 해결했다고 주장하지 않는다.

네이티브 앱은 기존 로그인 상태에서 최종 번들로 새로고침했고 홈을 표시했다. [네이티브 화면](native.png)을 보존했다. 이번 검사는 새 프로세스의 최초 실행이 아니므로 이전의 초기 빈 화면 원인은 여전히 미확인이다. 네이티브 원격 쓰기도 검사하지 않았다.

## 대용량 큐의 한계

450개 확인 기록, 45,303,433바이트(약 43.2MiB)를 넣고 접수 제한과 정리를 검사했다. Node 코어와 복제 기반 트랜잭션 어댑터를 사용했다. 외부 시간 제한은 30초, Node JavaScript 힙 제한은 512MiB였다.

신규 접수는 228.8ms에 거절됐고 기존 기록은 유지됐다. 정리는 752.4ms에 기록 450개를 제거했다. 검사 전체는 1.37초에 끝났지만 최대 RSS는 **1,376,416KiB, 약 1.31GiB**였다. 힙 제한은 전체 RSS 제한이 아니다.

이는 브라우저 IndexedDB의 메모리 측정값이 아니다. 실제 앱의 OOM을 재현한 것도 아니다. 다만 저장소 50MiB 상한이 실행 메모리 상한까지 보장하지는 않는다는 한계를 확인했다. [측정값](capacity.json)과 [실행 모델](capacity-probe.mjs)을 보존했다. 모델은 프로젝트 루트에서 `node --max-old-space-size=512 docs/research/2026-11-04-local-first-sync/reverification-2026-11-04/capacity-probe.mjs`로 실행할 수 있다.

대용량에서도 안전하다는 완료 판정은 보류한다. 다음 검증은 실제 브라우저의 큰 큐에서 메모리와 UI 지연을 측정하는 것이다. 저장소 전체를 복제하는 구조를 바꾸는 작업은 이번 확인 조건 보완에 포함하지 않았다.

실제 24시간 방치와 운영 환경 측정은 하지 않았다. 일일 조건은 시간을 전진한 검사와 실제 Worker 실행으로 확인했다. 기존 INDEX 크기 초과로 context 검사도 계속 실패한다.
