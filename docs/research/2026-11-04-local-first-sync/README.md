# 캐시 우선 표시와 5초 벌크 동기화 결과

캐시 우선 표시, 저장·게시 시 낙관적 반영, 5초 디바운스, 단일 커밋 벌크 저장과 복구 큐를 구현했다. 확인한 전송 기록만 별도 Worker가 24시간 간격으로 정리한다. 실제 사용자 콘텐츠는 수정하지 않았다.

## 구현한 정책

저장·게시 버튼을 누른 내용만 IndexedDB에 보관한 뒤 화면에 반영한다. 입력만으로 게시하지 않는다. 마지막 요청부터 5초가 지나면 전송한다. 요청이 계속 들어오면 타이머를 다시 시작하며 강제 최대 대기는 없다.

같은 문서의 미전송 수정은 최신본 하나로 합친다. 전송 중인 묶음은 고정한다. 이후 수정은 다음 묶음으로 남기며 확인한 선행 저장에만 기준 버전을 갱신한다. 여러 문서와 필요한 카테고리는 최대 20작업·4MiB 요청 하나와 원본 커밋 하나로 반영한다. 저장 충돌과 Origin·CSRF 검사는 유지했다.

통신·서버 오류는 5초·15초·60초 간격으로 최대 3회 재시도한다. 같은 요청 ID와 본문을 유지한다. 401·403·409와 후속 원격 수정은 자동 반복하지 않는다. 앱을 다시 열면 보관한 요청을 재개한다. 원격 확인 직후 앱이 종료돼도 확인 응답을 기기에 적용한 뒤 기록을 정리한다.

IndexedDB 트랜잭션과 만료되는 잠금으로 여러 창의 전송·정리 중복을 막는다. 확인 응답은 Web Locks와 버전 검사로 순서대로 적용한다. 응답의 요청 ID·SHA-256·커밋을 검사한다. 손상한 확인 기록은 남기고 다른 요청의 복구를 계속한다.

전송 저장소는 범위당 50MiB, 미전송 대상 100개, 보관 묶음 500개로 제한한다. 전송·응답을 기록할 여유도 미리 확보한다. 기록 500개에서는 새 전송을 멈추고 정리 후 재개한다. 한도를 넘는 신규 저장은 오류를 알리며 기존 편집을 삭제하지 않는다. 공개 캐시는 목록 하나와 방문한 본문 32개로 제한한다.

정리는 UI·동기화와 병렬로 실행한다. 마지막 정리에서 24시간이 지난 경우에만 시작한다. 앱이 꺼져 있으면 다음 실행 때 처리한다. 확인한 전송 기록 중 기기 반영까지 끝나고 해시가 일치한 기록만 지운다. 실패·미확인·편집 내용과 원본 캐시는 이 정리에서 지우지 않는다.

## 전후 실측

| 항목 | 이전 | 변경 후 |
|---|---:|---:|
| 실제 GitHub 카테고리 48개, 5회 중앙값 | 432.03ms | 0.37ms |
| 위 조회의 GitHub 요청 | 매번 1회 | 0회 |
| Chrome 반복 첫 화면, 3회 중앙값 | 508.4ms | 102.8ms |
| 위 화면의 목록 다운로드 | 매번 1회 | 0회 |
| 카테고리와 글 2개 HTTP 저장 | 1,233.72ms·3요청·3커밋 | 371.51ms·1요청·1커밋 |

실제 GitHub 측정은 같은 소유자 자격 증명으로 같은 카테고리를 읽었다. 두 경로의 원본 해시와 내용 해시는 모두 같았다. `refresh=1` 직접 조회와 같은 프로세스의 캐시 조회를 번갈아 실행했다. [원시 결과](live-category.json)와 [재현 코드](compare-live.mjs)를 보존했다. 위 수치는 서버 handler 시간이며 화면 시간은 아니다.

Chrome 측정은 같은 Mac·UI·임시 글 하나에 API 지연 350ms를 적용했다. 기준 번들은 현재 앱에서 `usePosts.ts`만 Git HEAD `a25208d8a5965f9688a6ecbb0d5be5ac26cc9a92`의 캐시 미적용 구현으로 교체해 만들었다. 처음 복사한 중간 번들에는 이미 읽기 캐시가 있어 기준에서 제외했다. 표는 기준을 교체한 뒤 마지막 반복 3회씩을 사용한다. 첫 글자 로딩부터 목록 DOM과 두 번의 animation frame을 관찰했다. [이전](browser-before.json)과 [변경 후](browser-after.json)를 확인한다.

HTTP 저장 비교는 같은 임시 GitHub 프로토콜 저장소에 카테고리와 글 2개를 저장했다. 각각의 요청에 350ms 지연을 적용했다. 표의 시간은 전송 시작부터 원격 확인까지다. **5초 디바운스 대기는 포함하지 않는다.** 벌크 재전송 뒤에도 커밋 수가 늘지 않았다. [측정값](http-bulk.json), [실행 결과](http-e2e.log), [검사 코드](../../../tests/e2e/local-first-bulk.test.mjs)를 보존했다.

## 실제 Chrome E2E

- 카테고리 저장 3회를 5초 안에 눌렀다. 로컬 접수는 약 4-15ms였고 원격 요청은 하나였다.
- 서버가 커밋을 만든 뒤 응답을 끊었다. 같은 요청 ID로 요청 두 개가 도착했지만 원본 커밋은 하나만 만들었다. Chrome의 전송 재시도가 개입할 수 있으므로 앱의 5/15/60초 재시도 증거와 구분한다.
- 글 저장 직후 5초 안에 새로고침했다. 목록에 로컬 변경을 표시하고 원격 저장을 재개했다. 원본 글 조회는 최초 한 번뿐이었다.
- 정리 Worker 두 개를 동시에 실행했다. 하나는 잠금 때문에 건너뛰었다. 다른 하나는 확인한 기록 3개를 304.4ms에 정리했다. 그동안 화면은 16프레임을 그렸다. 실패·미적용·해시 불일치 기록 3개는 남았다.
- 실제 글 편집·원격 저장·목록 반영을 확인했다. [글 저장 화면](post-saved.png), [응답 유실 복구 화면](recovered-save.png), [병렬 정리 화면](cleanup-workers.png)을 보존했다.

한 글 저장 표본에서는 브라우저가 긴 작업을 기록했고 전송 시작이 18초로 늦어졌다. 다른 표본의 로컬 접수는 약 68-87ms였다. 긴 작업의 정확한 원인은 확인하지 못했다. 5초 설정은 앱이 실행 가능한 동안의 디바운스 기준이며 실시간 전송 보장은 아니다. 카테고리의 짧은 접수 시간을 모든 편집에 일반화하지 않는다.

최종 번들을 만드는 동안 열려 있던 테스트 탭이 이전 청크를 참조해 한 번 실패했다. 이후 30분 제한 테스트 서버도 종료됐다. 이 두 상태는 제품 저장 실패와 구분했다. 최종 번들의 별도 임시 서버에서 다시 확인했다. 로컬 접수는 60-71ms였고 새로고침 뒤 한 요청·한 커밋으로 게시를 완료했다. [최종 실행 기록](browser-final.json)과 [완료 화면](final-recovered-save.png)을 보존했다.

## 실행한 검사와 제한

전체 `npm run check`는 556개 중 554개가 통과했다. 실패 2개는 작업 전 기록에도 있는 글 편집기의 카테고리 표시·취소 검사다. 이번 작업에서 임의로 고치거나 검사를 약화하지 않았다. [전체 결과](full-check.log)를 확인한다.

최종 관련 기능 검사 46개와 복구·용량 검사 11개는 모두 통과했다. 300번 저장 합치기, 대상 100개 한도, 4MiB 초과, 보관 기록 500개, 여러 소유자, 응답 유실 재개, 후속 수정 보존, 오래된 확인 역전과 손상 기록을 검사했다. [기능 결과](functional-check.log)와 [복구·용량 결과](bounds-check.log)를 보존했다.

복구·용량 검사는 Node 힙 256MiB와 외부 30초 제한에서 2.42초에 끝났다. `/usr/bin/time -l`의 RSS 보고는 샌드박스의 `kern.clockrate` 거부로 얻지 못했다. 실제 50MiB 큐의 지속 부하를 검증했다고 해석하지 않는다.

최종 빌드와 `git diff --check`를 통과했다. 마지막 표시 시각 보완 뒤 복구 검사 1개도 다시 통과했다. [후속 결과](recovery-final.log)를 보존했다. 기존 큰 번들 경고는 남았다. [빌드 결과](build.log)를 확인한다. 독립 읽기 검토의 발견 사항을 보완했고 마지막 검토에서 남은 정확성 지적은 없었다.

24시간 실제 방치는 하지 않았다. 시간을 전진한 검사와 실제 Worker 실행으로 일일 조건을 확인했다. 네이티브 앱의 기존 `Public content is not ready for this commit` 상태는 마지막 재시작 뒤 서버 조회에서 재현되지 않았다. 실제 서버가 글 3,033개를 약 584ms에 반환했다. 네이티브 홈과 반복 새로고침의 표시도 확인했다. 재시작 직후 빈 문서는 홈으로 다시 이동하자 표시됐다. 초기 빈 화면의 원인은 미확인이다. [관찰 기록](native-observation.json)과 [네이티브 화면](native-cache-home.png)을 보존했다. 새 쓰기 경로 E2E는 Chrome의 실제 앱과 임시 저장소에서 진행했으며 네이티브 원격 쓰기를 검증하지 않았다. 별도 공개 콘텐츠 작업은 변경하지 않았다.

커밋·푸시·배포는 하지 않았다. context 검사에는 기존 INDEX 크기 초과가 남았다.
