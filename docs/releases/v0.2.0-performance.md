### 전송량과 요청 수

| 단계 | GitHub 호출 | GitHub 쓰기 | 요청 body | 소비한 응답 |
| --- | ---: | ---: | ---: | ---: |
| 전송 최적화 전 | 33 | 10 | 11.444MB | 18.308MB |
| 전송 최적화 후 | 26 | 9 | 6.920MB | 11.165MB |
| 원본 저장과 공개 분리 후 | 12 | 4 | 1,275 bytes | 3,770,349 bytes |
| 단일 요청 저장 후 | 1 | 1 | 1,932 bytes | 377 bytes |

전송 최적화에서 요청은 39.5%, 소비한 응답은 39.0% 줄었다.
`generation.json` 캐시는 2,650,012→545,716 bytes로 줄었다. 공개 index의 5,560,675 bytes는 유지했다.
크기가 큰 독립 blob 업로드는 최대 2개를 병렬 실행한다. 실제 세 저장에서는 이 병렬 효과를 측정하지 않았다.
MB는 십진 단위다. 요청은 HTTP·TLS header를 제외한 body다. 응답은 압축 전송량이 아닌 디코딩 후 소비량이다.

원자적 저장 표는 준비된 제목 수정만 포함한다. 최초 원본 준비는 조회 3회와 mutation 1회가 필요했다.
대용량은 기존 Git-data 경로를 사용하며 추가 요청이 생긴다. 응답 복구도 읽기 요청이 생긴다.
실제 수락 요청을 다시 확인했을 때 추가 mutation은 0회였다. 같은 커밋을 반환했고 확인 파일도 검증했다.

공개 workflow는 별도로 실행한다. 제목 표본마다 23호출·5쓰기였다.
원본과 공개를 합친 관측은 35→24호출, 9→6쓰기다. 상태 확인·OAuth·checkout·감사는 제외한다.
전체 작업이 네트워크 요청 한 번이라는 뜻은 아니다.
단일 요청 단계의 공개 준비 추정 중앙값은 73.907초였다. 서로 다른 시계의 오차는 측정하지 않았다.
즉시 전송 단계의 서버 POST는 1.504/1.570/1.573초였다. 주된 개선은 서버 가속이 아니라 5초 대기 제거다.

실측마다 임시 글 생성·제목 수정 3회·삭제와 실제 공개 workflow 5회 성공을 확인했다.
늦은 이전 workflow는 쓰기 0회로 최신 공개본을 유지했다.
기존 원본 SHA는 단계별 감사에서 보존했다. 글 3,032개와 3,033개였던 세션을 구분한다.
단일 요청 단계는 기존 10,292개 파일을 보존하고 확인 파일 5개를 남겼다.
즉시 전송 단계는 기존 10,297개 파일의 SHA를 보존했다. 정상 확인 파일은 복구 계약 때문에 유지한다.
