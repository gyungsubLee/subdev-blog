# main 커밋을 검사하고 운영 블로그에 배포한다

목표: main push의 정확한 SHA를 검사·빌드하고, 최신 main과 일치할 때만 운영 주소를 연결한다.
사용자가 CI/CD 수정과 실제 적용을 요청했다. 별도 체크아웃에서 실행하며 다른 작업의 수정은 보존한다.

## 결정과 범위

- `.github/workflows/deploy-main.yml`이 운영 주소 연결을 전담한다. main push와 main의 수동 재실행을 지원한다.
- checkout은 실행 SHA로 고정한다. `npm ci`, Vercel 빌드, 기존 전체 검사와 콘텐츠 검사를 거친다. native preview 검사가 빌드 파일을 요구하므로 먼저 빌드한다.
- 동시 실행을 직렬화한다. 배포 직전과 운영 연결 직전에 원격 main을 확인해 오래된 실행을 건너뛴다.
- `scripts/deploy-main.mjs`가 CI 실행·작업 트리·빌드 식별자·프로젝트·배포 메타데이터·HTTP 상태를 검증한다.
- 콘텐츠 게시 워크플로는 후보 검증을 유지하지만 운영 주소를 직접 변경하지 않는다. 설치 토큰으로 main을 갱신하면 새 워크플로가 동작한다.
- 기존 수동 alias helper를 차단한다. 이전 콘텐츠 실행의 선택적 alias 변수는 제거하고 새 운영 변수로 이전한다.
- 운영에만 존재한 승인 브랜드·책 파비콘 4개 파일도 Git에 기록한다. 승인한 UI를 유지하기 위한 필수 변경이다.
- Vercel 소유자가 API/CLI로 직접 연결하는 행위까지 이 코드가 차단한다고 주장하지 않는다. AGENTS.md에 운영 배포 절차를 고정한다.

## 실행

1. 수동 실행, 오래된 SHA, 다른 프로젝트, 잘못된 산출물, 연결 직전 main 변경을 거부하는 검사를 작성하고 실패를 확인한다.
2. 운영 helper와 워크플로를 구현하고 기존 콘텐츠 검증을 보존하며 alias 쓰기만 제거한다.
3. 원격 설정을 새 변수와 main 전용 production 환경으로 연결한다. 비밀값은 기존 값을 재사용하며 출력하지 않는다.
4. 관련 검사와 전체 검사·빌드를 실행한다. 변경을 커밋하고 main에 일반 push한다.
5. 해당 SHA의 Actions를 끝까지 확인한다. 배포의 build-info와 main SHA, 운영 줄노트·파비콘 표시를 대조한다.

## 집중 확인

- 실패한 검사와 잘못된 산출물은 운영 주소를 변경하지 않는다.
- 새 main이 도착하면 오래된 실행과 재실행은 운영 주소를 변경하지 않는다.
- HTTP 오류·잘못된 프로젝트·다른 실행의 배포는 비밀값 노출 없이 거부한다.
- 콘텐츠 게시 검증·토큰 회수·main 갱신은 유지한다.
- 운영 로고·파비콘·줄노트는 Git과 실제 배포에 함께 포함된다.

## 상태

구현 완료. 로컬 전체 검사 676개, 콘텐츠 검사, 빌드가 통과했다. 최신 워크플로 순서를 확인하는 6개 검사도 통과했다.
이전 helper의 운영 연결 거부와 콘텐츠 preview 검증을 포함한 28개가 통과했다.
처음 전체 검사에서는 서버 포트 권한 2개와 기존 브랜드 기대값 1개가 실패했다. 권한과 승인된 제목을 반영한 최종 실행은 676개 모두 통과했다.
GitHub는 빈 변수 값을 허용하지 않아 CMS_PREVIEW_ALIAS를 제거했다. BLOG_PRODUCTION_ALIAS와 main 전용 production 환경을 설정했다.
실제 main push부터 운영 반영까지의 검증은 다음 단계다. 검사 담당자와 배포 담당자는 이 채팅의 Codex다.
