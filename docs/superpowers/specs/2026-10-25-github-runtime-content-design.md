# GitHub 원본을 조회하고 직접 저장하는 설계

2026-10-25 KST. 사용자는 기존 GitHub 연동을 재사용하는 구현을 요청했다.
이 문서는 이전 GitHub 콘텐츠 관리 설계의 조회·게시 경로를 대체한다.

## 목표

일반 방문자는 서버 API에서 콘텐츠 저장소의 글을 읽는다.
글과 분류를 저장하면 콘텐츠 저장소의 기준 브랜치만 갱신한다.
저장 때문에 앱 커밋, Actions 실행 또는 Vercel 배포를 만들지 않는다.
서브모듈은 로컬 작업과 앱 릴리스의 콘텐츠 기준을 기록한다.

## 공개 조회

- `GET /api/public?kind=index`는 `{posts,categories,contentCommit}`을 반환한다.
- `GET /api/public?kind=post&id=<UUID>&commit=<SHA>`는 같은 커밋의 공개 Post를 반환한다.
- 목록은 본문을 1400자로 제한하고 `bodyLoaded:false`를 유지한다.
- 본문·목록·분류·첨부는 같은 커밋을 사용한다.
- 서버는 기존 GitHub 클라이언트와 문서 파서·공개 변환 함수를 재사용한다.
- GitHub REST API로 기준 커밋과 트리를 읽는다. 공개 파일은 고정 커밋의 raw 주소로 읽는다.
- 고정 콘텐츠 저장소가 공개 저장소인지 확인한다. 다른 저장소와 비공개 저장소를 요청으로 선택할 수 없다.
- `GITHUB_PUBLIC_TOKEN`은 선택한 서버 전용 읽기 토큰이다. 토큰이 없으면 공개 읽기를 시도한다.
- 로그인 설정과 세션 오류가 공개 조회를 막지 않는다.
- 서버 캐시는 최대 30초다. `after=<저장 SHA>` 요청은 이전 커밋의 캐시를 다시 확인한다.
- 첨부는 검증한 저장소·콘텐츠 SHA의 raw URL을 사용한다. 임의 외부 프록시는 만들지 않는다.
- GitHub 오류와 제한 초과를 빈 목록이나 이전 빌드 콘텐츠로 숨기지 않는다.
- 네트워크 요청과 병렬 읽기에 유한한 제한을 둔다. 캐시 크기를 제한한다.
- 링크 누락은 공개 화면 전체를 중단하지 않는다. URL 안전 검사와 HTML 정화는 유지한다.

## 기준 목록과 응답 크기

실제 콘텐츠는 3,032편이다. 서버가 시작될 때 모든 본문을 다시 내려받지 않는다.
빌드는 서버 전용 `server/content-catalog.json`에 원본 메타데이터·1400자 요약·Git blob ID·revision·첨부 이름·전체 링크 참조를 기록한다.
실행 중에는 GitHub의 실제 트리와 비교하고 바뀐 문서만 다시 읽는다. 상세 조회는 해당 본문만 읽는다.
삭제 참조 검사도 일치하는 blob의 전체 참조 목록을 재사용한다. 요약을 전체 본문으로 오인하지 않는다.
GitHub 오류와 데이터 변경을 이전 기준 목록으로 숨기지 않는다.

공개 JSON은 1 MiB를 넘으면 클라이언트가 허용하는 gzip으로 압축한다.
압축 후 응답도 4 MiB 안에 있어야 한다. gzip을 거부하는 큰 응답에는 오류를 반환한다.
작은 응답은 기존 JSON 형태를 유지한다. 글 수와 본문 요약 범위를 줄이지 않는다.

## 직접 저장

- 현재 `/api/content`와 `/api/assets`의 인증·CSRF·문서·첨부 검사를 재사용한다.
- 요청 ID와 입력 지문을 가진 후보 커밋·요청 브랜치를 유지한다. 응답 유실 시 같은 커밋을 복구한다.
- 기준 HEAD와 문서 revision이 달라지면 충돌로 끝낸다.
- 콘텐츠 브랜치를 `force:false`로 갱신한다. 요청 결과가 기준 브랜치에 포함됐는지 확인한 뒤 `published`를 반환한다.
- 기준 브랜치 갱신 응답이 유실돼도 HEAD와 계보를 확인한다. 다른 변경을 덮어쓰지 않는다.
- 본문 수정은 해당 문서의 직렬화·URL·경로·버전을 검사한다. Markdown과 분류 원본은 각각 2 MiB 이하로 제한한다.
- 글·분류 삭제는 기존 참조·하위 관계 정책을 유지한다. 분류 배정도 존재 여부를 확인한다.
- `/api/publish` GET은 상태만 확인한다. POST만 기존 요청을 재시도하며 인증·Origin·CSRF 검사를 요구한다. Actions를 호출하지 않는다.
- 연결 확인에서 활성 게시 workflow와 Actions 쓰기 권한을 필수 조건으로 요구하지 않는다.
- 기존 GitHub App 권한은 확장하지 않는다. 기존 Actions 권한이 있어도 연결을 유지한다.

## 화면

- `usePosts`는 공개 API를 호출한다. 인증 확인을 기다리지 않는다.
- 저장·삭제·분류 변경이 완료되면 공개 목록과 본문을 새 커밋 기준으로 다시 읽는다.
- `PublishStatus`는 직접 저장된 요청에 Actions 폴링을 시작하지 않는다.
- 기존 초안·재시도 ID·편집 내용 보존을 유지한다.
- 저장 문구에서 배포와 게시 검증 대기를 제거한다.

## 검증

기존 Node test runner와 JSDOM을 사용한다. 새 의존성을 추가하지 않는다.
공개 조회, 직접 저장, 재시도, 충돌, 삭제 참조, 즉시 재조회에 회귀 검사를 둔다.
전체 검사와 빌드는 마지막 통합 상태에서 한 번 실행한다.
Chrome에서 실제 공개 GitHub 조회를 확인한다. 원격 저장 검사는 공개 콘텐츠를 변경하지 않는 테스트로 구분한다.
이 변경을 운영하려면 앱 코드를 한 번 배포해야 한다. 이번 요청은 원격 배포를 포함하지 않는다.
