# 콘텐츠 submodule과 AI 메타데이터 리팩터링 설계

작성일: 2026-10-23 KST

상태: 문서 검토·수정 완료, 구현 미착수

표면: STE-KO 문서

실행 계획: [실행 계획](../plans/2026-10-23-content-submodule-ai-metadata.md)

글 원본은 별도 Git 저장소에 보관한다. 앱은 이 저장소를 `content/` submodule로 연결한다.
각 글은 고정 ID 폴더 안에 실제 제목의 Markdown과 첨부 파일을 함께 둔다.
카테고리와 부모·자식 관계는 메타데이터로 관리한다. 분류 변경으로 원본 폴더를 이동하지 않는다.

이 문서는 합의한 리팩터링 계약이다. 앱 코드, 콘텐츠, 저장소 연결과 배포 설정은 이번 문서 작업에서 변경하지 않는다.

## 1. 목표와 범위

### 1.1 필수 결과

- F01: 공개 콘텐츠 저장소를 앱의 `content/` Git submodule로 연결한다.
- F02: `content/posts/<글 UUID>/<실제 제목>.md`와 해당 글의 첨부 파일을 같은 깊이에 둔다.
- F03: 글 ID를 유지하고, 글 계층과 카테고리 계층을 별도 메타데이터로 표현한다.
- F04: 주제·요약·별칭·문서 관계·출처·검토 상태를 AI가 읽을 수 있게 보존한다.
- F05: frontmatter와 AI 필드는 게시 본문, 목록, 미리보기와 글쓰기 본문에 표시하지 않는다.
- F06: 가져오기, 초안 저장, 백업과 내보내기가 메타데이터와 정식 글 ID를 보존한다.
- F07: 현재 게시 내용, 이미지, 코드, 앵커, 원문 계층과 기존 웹 주소를 보존한다.
- F08: 공개 원본과 구분한 로컬 LLM wiki의 출처 추적 및 색인 계약을 마련한다.
- F09: submodule을 포함한 새 체크아웃에서 로컬 원문 보관 폴더 없이 검사하고 빌드한다.

### 1.2 이번 리팩터링의 경계

원본 저장 방식, 변환 단계와 문서 계약을 바꾼다. 목록·게시 화면과 본문 지연 로딩은 유지한다.
글쓰기에는 원문을 보존하는 본문 입력을 마련한다. 로컬 지식 색인 형식과 에이전트 작업 규칙은 문서로 확정한다.
색인 생성기와 wiki 앱은 후속 작업으로 남긴다.

다음 기능은 포함하지 않는다.

- 서버 계정, 웹에서 GitHub로 직접 발행하는 기능, 기기 간 초안 동기화.
- 자동 AI 호출, 유료 API 연결, 모든 글의 요약을 일괄 생성하는 작업.
- 벡터 DB, 임베딩 검색, CRDT, 별도 백엔드와 협업 서버.
- 카테고리를 반영한 원본 폴더 재배치와 이미지의 Mermaid 자동 변환.
- 기존 Notion 수집·복구·이미지 변환 도구의 CLI 전면 개편.

코드와 Mermaid 원문은 Markdown 본문에 보존한다.
현재 수식·HTML 렌더링을 유지한다. Mermaid의 실제 도식 렌더링은 별도 UI 작업으로 다룬다.

## 3. 저장소와 파일 배치

아래 제목과 이미지 파일명은 실제 데이터에서 확인했다. 디렉터리 배치는 변경 후 목표다.

```text
subdev-blog/                              # 앱 저장소
├── .gitmodules
├── content/                              # 공개 콘텐츠 Git submodule
│   ├── README.md
│   ├── AGENTS.md                         # AI의 읽기·보강·검토 규칙
│   ├── CONTENT_SCHEMA.md                 # 필드·직렬화·관계 계약
│   ├── categories.json
│   └── posts/
│       ├── 1c3eda9b-0fe1-819c-beab-c6a3a1072bb9/
│       │   ├── 리액트.md
│       │   └── 35cde7f29524d65a.webp
│       ├── 1d4eda9b-0fe1-80a2-95f7-e975482b1dcd/
│       │   ├── React + GSAP.md
│       │   └── ee7da0b7cbb72014.webp
│       └── 1dceda9b-0fe1-80d4-80ac-ee6d24a0638c/
│           ├── z-index 적용한됨.md
│           ├── 19ed92dd13daa7ad.webp
│           └── 2e517ee72bc3809a.webp
├── scripts/
├── src/
└── public/content/                       # 생성 결과, 앱 Git에서 제외
```

제안하는 콘텐츠 저장소 이름은 `subdev-blog-content`다.
실제 소유자와 HTTPS URL은 submodule 연결 단계에서 확인한다. 이번 문서 작업은 저장소를 만들지 않는다.

### 3.1 글 폴더 규칙

- 기존 UUID를 소문자와 하이픈 형식으로 정규화한다. 바뀌지 않는 글 식별자로 사용한다.
- 폴더 하나에는 본문 `.md`를 정확히 하나 둔다.
- 제목이 같은 글도 ID가 다르면 서로 다른 폴더에 보관한다.
- 파일명은 제목을 NFC로 정규화한 뒤 경로 금지 문자와 제어 문자를 `_`로 바꾼다.
- 끝의 점·공백을 제거한다. Windows 예약 이름에는 `_`를 앞에 붙인다.
- 확장자를 포함해 UTF-8 200바이트를 넘으면 코드 포인트 경계에서 줄인다.
- 빈 파일명은 `제목 없음.md`를 사용한다. 원래 제목은 `title`에 그대로 보존한다.
- 제목 변경은 같은 ID 폴더 안의 `.md` 이름만 바꾼다. 새 파일 저장을 확인한 뒤 이전 파일을 제거한다.

Markdown·이미지·첨부 파일을 가리키는 경로는 해당 글 폴더를 기준으로 해석한다.
글의 분류와 부모 변경은 파일명 및 이미지 경로를 바꾸지 않는다.

## 4. 문서와 메타데이터 계약

### 4.1 원본 예시

```yaml
---
schema_version: 1
id: "1dceda9b-0fe1-80d4-80ac-ee6d24a0638c"
title: "z-index 적용한됨"
parent_id: "1d4eda9b-0fe1-80a2-95f7-e975482b1dcd"
order: 0
kind: "troubleshooting"
summary: "footer 요소의 z-index 겹침 문제를 CSS 코드와 화면으로 기록하고, 원인 분석과 수정 과정을 정리한 글."
tags:
  - "css"
  - "z-index"
  - "stacking-context"
  - "flexbox"
aliases:
  - "z-index가 적용되지 않는 문제"
  - "footer 레이어 겹침"
related_ids: []
source_ids: []
source_url: "https://beautiful-college-c84.notion.site/1dceda9b0fe180d480acee6d24a0638c"
review_status: "unreviewed"
created: "2025-04-21T02:48:47.208Z"
updated: "2025-04-21T06:22:27.987Z"
---

# z-index 적용한됨

![문제 화면](./19ed92dd13daa7ad.webp)

본문과 코드, Mermaid 원문을 여기에 둔다.
```

예시의 요약은 주제를 설명한다. 본문의 기술 주장을 검증했다는 뜻은 아니다.
`category_id`가 없는 글은 부모 글의 분류를 상속한다.

### 4.2 필드

| 필드 | 타입과 기본값 | 계약 |
|---|---|---|
| `schema_version` | 정수 `1` | 다른 주 버전은 오류로 처리 |
| `id` | UUID 문자열 | 폴더 ID와 일치, 가져오기 후에도 유지 |
| `title` | 문자열 | 사람이 작성한 제목, 내용 임의 교정 금지 |
| `parent_id` | UUID 또는 `null` | 원문 루트 `Main`은 `null` |
| `category_id` | 선택 문자열 | 생략하면 부모의 분류 상속 |
| `order` | 0 이상의 정수, 기본 `0` | 동순위는 ID로 정렬 |
| `kind` | 열거 문자열, 기본 `article` | `article`, `troubleshooting`, `concept`, `reference`, `synthesis` |
| `summary` | 문자열, 기본 빈 문자열 | 주제·범위를 1-3문장으로 설명 |
| `tags` | 문자열 배열, 기본 `[]` | 본문에서 확인한 핵심 개념 |
| `aliases` | 문자열 배열, 기본 `[]` | 검색용 다른 표현 |
| `related_ids` | UUID 배열, 기본 `[]` | 의미상 연결, 부모 관계와 구분 |
| `source_ids` | UUID 배열, 기본 `[]` | 내용을 작성할 때 사용한 근거 문서 |
| `source_url` | 선택 HTTP·HTTPS URL | 원문의 공개 주소 |
| `review_status` | 문자열, 기본 `unreviewed` | `unreviewed`, `reviewed`, `needs_review` |
| `created`, `updated` | ISO 날짜·시간 문자열 | 기존 날짜 보존, 실제 변경 때만 수정 |
| `cover`, `icon` | 선택 문자열 또는 `null` | 로컬 파일·공개 URL·기존 아이콘 표현 보존 |
| `legacy_path` | 선택 문자열 | 이전 Markdown 경로를 해석하기 위한 별칭 |
| `legacy_category` | 선택 문자열 | 이전 글의 원문 분류, 현재 분류의 호환 값 선택에만 사용 |

알 수 없는 필드는 JSON 호환 값으로 보존한다. 확장 필드를 공개 출력에 자동 포함하지 않는다.
YAML 주석과 줄바꿈 모양의 보존은 요구하지 않는다. 필드의 의미값과 본문은 보존한다.

### 4.3 파서와 검증

공통 파서는 전체 문서·수정본·기존 형식을 구분한다. 전체 문서는 `{ metadata, markdown }`을 포함한다.
수정본에는 정식 문서의 필수 필드나 AI 기본값을 채우지 않는다. 각 모드의 `markdown`에는 frontmatter가 들어가지 않는다.
기존 `parseMarkdownDocument`와 `markdownDocument`를 확장하고, 기존 호출용 필드는 호환 어댑터로 유지한다.
`document_mode`와 `base_revision`은 가져오기·내보내기용 필드다. 정식 원본의 메타데이터로 저장하지 않는다.

YAML 1.2 매핑을 읽기 위해 `yaml@2`를 사용한다.
현재 직접 의존성에는 YAML 파서가 없다. 배열·여러 줄 문자열·확장 필드 때문에 자체 YAML 파서를 만들지 않는다.
실행 단계에서만 의존성을 추가하고 lockfile에 실제 버전을 기록한다.

- 중복 키, 비문자열 키, 사용자 태그와 YAML 별칭을 거부한다.
- 유한 숫자·문자열·불리언·null·배열·일반 객체만 허용한다.
- `__proto__`, `constructor`, `prototype` 키는 중첩 위치에서도 거부한다.
- 알려진 필드의 타입과 ID 참조를 검사한다. 경로 이탈과 심볼릭 링크의 폴더 탈출을 거부한다.
- 첫 구분선 사이가 YAML 매핑이 아니면 일반 Markdown 구분선으로 보존한다.
- 메타데이터 키가 있는 헤더가 잘못됐으면 오류로 중단한다. 헤더를 본문에 흘려보내지 않는다.
- frontmatter 없는 일반 Markdown과 기존 내보내기 형식도 읽는다. 정식 저장 때 스키마 1로 정규화한다.

기존 10MiB 문서 가져오기 제한과 5MiB 이미지 업로드 제한은 유지한다.
알 수 없는 필드만 있는 유효한 YAML 헤더도 본문에서 분리한다.
정식 본문의 첫 H1은 그대로 보존한다. 제목 추가·제거의 기존 동작은 기존 형식의 호환 어댑터로 한정한다.

## 5. 카테고리와 글 계층

`categories.json`은 다음 레코드의 배열이다.

```json
[
  {
    "id": "group:frontend",
    "name": "프론트엔드",
    "parent_id": null,
    "order": 0,
    "sources": []
  },
  {
    "id": "source:리액트",
    "name": "리액트",
    "parent_id": "group:frontend",
    "order": 0,
    "sources": ["리액트"]
  }
]
```

`id`는 이름 변경 뒤에도 유지한다. `sources`는 기존 분류 문자열과 브라우저 설정을 연결하는 호환 값이다.
이전한 글은 선택 필드 `legacy_category`에 기존 분류 문자열을 보존한다.
공개 `Post.category`는 유효한 `legacy_category`를 사용한다. 현재 분류의 `sources`에 없으면 카테고리 ID를 호환 값으로 사용한다.
새 글도 카테고리 ID를 호환 값으로 쓴다. `group:unclassified`의 기본 호환 값은 `미분류`다.
여러 분류를 합쳐도 `sources[0]`로 글의 기존 분류를 추측하지 않는다.
공개 카테고리의 `sources`에는 해당 ID를 추가한다. 화면 표시 이름은 `categoryId`로 정식 카테고리를 찾아 사용한다.
폴더 이름에 카테고리를 넣지 않으므로 `CI/CD`도 원래 표시명을 유지한다.

- 글 계층은 글의 `parent_id`로 구성한다. 글 계층의 순환과 없는 부모를 오류로 처리한다.
- 카테고리 계층은 카테고리의 `parent_id`로 구성한다. 글 계층과 독립적으로 검사한다.
- 가장 가까운 글 조상의 명시적 `category_id`를 상속한다. 직접 지정한 값이 우선한다.
- 직접 지정한 분류는 부모를 이동해도 유지한다. 잘못된 명시적 분류는 미분류로 숨기지 않는다.
- 상속할 분류가 없는 글은 생성 데이터에서 미분류로 표시한다. `Main`은 이 경우를 허용한다.
- 글·카테고리 ID가 중복되거나 카테고리의 `sources`가 중복되면 빌드를 중단한다.

이전 시 각 원문 카테고리 시작 글에만 분류 ID를 지정한다.
계산한 분류가 기존 `Post.category`와 다르면 그 글에 분류를 직접 지정하고 차이를 보고한다.
`Main`에는 `source:Main`을 직접 지정한다. 이 카테고리는 `group:unclassified` 아래에 두고 `sources: ["Main"]`을 보존한다.
분류 없는 새 글의 생성 값은 `categoryId: "group:unclassified"`, `category: "미분류"`다. 미분류 노드의 `sources`에 `미분류`를 포함한다.

정식 분류는 콘텐츠 저장소에서 변경한다. 현재 웹의 분류 편집은 브라우저 개인 설정으로 유지한다.
`second-brain:categories:v1`과 `:v2`는 삭제하지 않는다. 정식 트리 위에 개인 설정을 적용하되 원본을 덮어쓰지 않는다.
저장한 개인 설정이 없으면 정식 트리를 사용한다. 유효한 기존 설정은 ID와 `sources`로 연결하고 새 정식 분류를 보충한다.
개인 이름·배치가 정식 변경보다 우선한다. 손상된 설정은 정식 트리로 표시하되 기존 저장 값을 덮어쓰지 않는다.
개인 설정을 정식 저장소에 반영하는 기능은 이번 범위에 없다.

이름 변경과 상위 분류로 묶기는 `categories.json`만 바꾼다.
카테고리 ID를 없애는 실제 병합은 그 ID를 직접 지정한 글의 `category_id`도 바꿔야 한다.
상속한 자식 글은 개별 수정하지 않는다. 어느 경우에도 글 폴더와 첨부를 이동하지 않는다.

## 6. 이미지·첨부·글 링크

현재 웹에서 사용하는 파일 바이트를 이전한다. 대용량 원본을 다시 변환하지 않는다.
`assetMap[원래 URL] ?? 원래 URL`로 실제 공개 파일을 찾는다.
표지·아이콘과 본문의 참조를 읽고, 같은 파일을 해당 글 폴더에 한 번만 복사한다.
다른 글에서 같은 이미지를 사용하면 각 글 폴더에 복사한다.

- Markdown 링크·이미지·참조 링크와 HTML `src`·`href`·`srcset`을 처리한다.
- 코드 블록·인라인 코드·HTML `code`·`pre` 안의 예제 경로는 수정하거나 첨부로 수집하지 않는다.
- 기존 HTML 앵커, entity, GFM, 수식과 코드 바이트를 보존한다.
- 확보한 로컬 파일이 없으면 오류로 보고한다. 기존 외부 URL은 유지하고 외부 의존 목록에 기록한다.
- 남는 공개 파일도 이전 보고서에 나열한다. 소유 관계를 확인하기 전에는 삭제하지 않는다.
- 파일 해시를 비교해 이전 바이트가 현재 공개 파일과 같은지 확인한다.

원본 이미지는 `./19ed92dd13daa7ad.webp`처럼 참조한다.
게시용 이미지는 `/content/assets/<글 ID>/<파일명>`으로 생성한다.
게시용 URL에는 카테고리와 제목을 넣지 않는다.

새 글 간 링크는 `#/post/<글 ID>`와 기존 블록 fragment를 사용한다.
기존 글 주소를 보존한다. 옛 첨부 URL을 외부에서 직접 참조한 경우의 호환은 이번 범위에 포함하지 않는다.
이전 Markdown 경로와 Notion 주소는 ID를 찾아 이 형식으로 변환한다.
이 규칙은 웹에 맞춘 계약이다. 원본 Markdown 뷰어에서의 직접 파일 이동은 보장하지 않는다.
로컬 wiki는 색인의 ID→파일 경로 표를 사용해 원문을 연다.

`pageLink`는 첨부 URL을 글 링크로 오인하면 안 된다.
`/content/assets/<글 ID>/첨부.pdf`에 ID가 포함돼도 그대로 첨부 URL을 반환해야 한다.

PNG·WebP·GIF·SVG·PDF·ZIP·MOV·JSON은 현재 보유 파일 형식을 유지한다.
첨부 경로의 CSP는 기존 `/notion/assets/` 보호와 동등하게 적용한다.
원본 코드의 `/images/logo/...`처럼 실행 예제에만 나오는 경로는 콘텐츠 첨부로 간주하지 않는다.

## 7. 원본·공개 데이터·초안 분리

### 7.1 세 가지 문서 표현

| 표현 | 저장 위치 | 포함 정보 |
|---|---|---|
| `ContentDocument` | 콘텐츠 저장소의 `.md` | 전체 메타데이터와 원본 본문 |
| 공개 `Post` | 생성 JSON과 브라우저 | 공개 필드, 표시용 본문과 revision |
| 편집 초안 | 기존 localStorage | 로컬 초안 ID, 정식 문서 ID, 본문 블록과 보존 메타데이터 |

공개 `Post`의 허용 필드는 다음으로 고정한다.
`id`, `title`, `parentId`, `category`, `categoryId`, `createdAt`, `updatedAt`, `markdown`, `path`, `url`, `excerpt`, `cover`, `icon`, `order`, `revision`, `bodyLoaded`.
`draft`는 브라우저 초안의 기존 필드다. 정식 게시 출력에는 넣지 않는다.

`summary`, `tags`, `aliases`, `related_ids`, `source_ids`, `review_status`, `legacy_path`, `legacy_category`와 확장 필드는 공개 JSON에서 제외한다.
본문, 제목, 날짜와 화면의 카테고리는 기존 UI에서 사용할 수 있다.
AI 전용 표식 검사는 제목·본문에 의도적으로 쓴 문구까지 지우는 검사가 아니다.
검색 미리보기와 `excerpt`는 메타데이터를 제거한 본문에서만 만든다.
색인의 본문 미리보기는 현재처럼 1,400자를 유지한다. 전체 검색 확장은 이번 범위에 없다.

`revision`은 정식 `.md` 파일 바이트의 SHA-256이다.
게시용 URL로 바꾸기 전 원본 파일을 기준으로 계산한다. 숨긴 필드가 바뀌어도 충돌을 보수적으로 감지한다.
공개 출력에는 원본 `.md`, 백업, 블록 JSON과 로컬 wiki를 복사하지 않는다.
공개 콘텐츠 저장소의 frontmatter는 GitHub에서 읽을 수 있다. 화면 미표시는 비공개 저장을 뜻하지 않는다.
개인 wiki와 비공개 메모는 콘텐츠 저장소 밖에 둔다.

### 7.2 글쓰기와 왕복 보존

- 기존 `draft-UUID`는 브라우저 저장 키로 유지한다. 정식 문서 ID와 구분한다.
- 새 글은 정식 UUID를 한 번 생성한다. 자동 저장과 반복 내보내기에서 ID를 바꾸지 않는다.
- 정식 Markdown을 가져오면 `metadata.id`를 정식 문서 ID로 사용한다.
- 스키마 1 정식 문서의 `id`와 `source_id`가 충돌하면 오류로 처리한다.
- 스키마 없는 기존 내보내기는 유효한 `source_id`를 우선한다. 이 경우 `id`는 초안 별칭이다.
- 유효한 `source_id`가 없으면 유효한 `id`를 정식 ID로 사용한다. 둘 다 없으면 새 UUID를 한 번 생성한다.
- 편집기에는 frontmatter 없는 본문만 전달한다. 원시 YAML과 AI 필드의 UI를 추가하지 않는다.
- 제목·분류는 기존 일반 입력으로 다룬다. 분류 값은 선택한 카테고리 ID로 연결한다.
- 전체 문서를 읽은 초안은 메타데이터를 별도 상태로 보존한다. JSON 백업도 같은 정보를 유지한다.
- 기존 글과 가져온 Markdown은 본문 전용 Markdown 입력으로 편집한다. frontmatter는 이 입력에 넣지 않는다.
- 새 블록 글과 기존 블록 초안은 BlockNote를 유지한다. 기존 Markdown을 BlockNote로 자동 변환하지 않는다.
- 제목·분류만 바꾸거나 내보내기만 하면 원문 본문을 그대로 사용한다. HTML·앵커·수식·Mermaid·코드를 재직렬화하지 않는다.
- 알 수 없는 필드는 의미값을 보존한다. 손상된 초안을 덮어쓰지 않는다.
- 본문이 바뀌면 `review_status`를 `needs_review`로 바꾼다. 요약을 새 내용처럼 자동 확정하지 않는다.

공개 화면의 Markdown 다운로드는 메타데이터 없는 본문을 제공한다.
작성 화면의 내보내기는 전체 원본 또는 아래 수정본 계약을 사용한다.
두 파일의 용도를 `CONTENT_SCHEMA.md`에 구분해 기록한다.

전체 문서를 가져온 초안은 입력 파일의 SHA-256을 기준 revision으로 보관한다.
이미 `base_revision`이 있는 전체 편집본을 다시 가져오면 그 값을 유지한다. 편집본 파일의 해시로 바꾸지 않는다.
전체 편집본 내보내기는 이 값을 `base_revision`으로 전달한다. 기존 정식 ID를 갱신할 때는 전체 편집본도 revision 검사를 통과해야 한다.
새 ID의 첫 저장에는 기준 revision을 요구하지 않는다. 기존 ID인데 기준 값이 없으면 쓰기를 중단한다.
브라우저의 전체 편집본도 오래된 AI 필드로 최신 원본을 덮어쓰면 안 된다.

### 7.3 공개 사이트에서 시작한 편집

공개 `Post`에는 숨긴 메타데이터가 없다. 브라우저가 이 값을 임의로 재구성하지 않는다.
정식 문서 전체를 읽지 않은 편집은 `document_mode: patch`를 가진 수정본으로 내보낸다.
수정본 헤더는 `schema_version: 1`, `document_mode: patch`, `id`, `base_revision`, `title`과 변경한 `category_id`를 포함한다.
파서는 수정본에 정식 문서의 `parent_id`와 AI 필드를 요구하지 않는다.
본문은 새 본문이다. 카테고리 미변경은 필드 생략으로 표현한다.

로컬 가져오기는 다음 순서를 따른다.

1. 정식 ID로 원본 파일을 찾는다. 없는 원본에 수정본을 적용하지 않는다.
2. `base_revision`을 현재 원본의 SHA-256과 비교한다. 다르면 쓰기 전에 중단한다.
3. 제목·본문·명시적으로 변경한 분류만 합친다. ID·부모·출처·확장 필드는 기존 값을 보존한다.
4. 수정된 본문은 `needs_review`로 표시하고 수정일을 갱신한다.
5. 첨부를 검증하고 임시 파일에 저장한다. 검증 성공 뒤 원본을 교체한다.

기준 값이 없는 전체 문서나 기존 형식은 로컬에서 diff를 검토하고 `--expected-revision <SHA-256>`을 명시해야 기존 ID에 적용할 수 있다.
파일과 옵션의 기준 값이 다르면 중단한다. 수정일 확인이나 강제 적용 옵션으로 revision 검사를 우회하지 않는다.

### 7.4 업로드 이미지

현재 편집기의 data URL은 초안에서 유지할 수 있다.
브라우저의 전체 문서 가져오기는 `.md`와 형제 첨부를 함께 선택할 수 있게 한다. 선택하지 않은 로컬 파일은 읽지 않는다.
선택한 첨부는 이름과 바이트를 초안·JSON 백업에 보존한다. 미리보기의 임시 URL은 Markdown이나 백업에 저장하지 않는다.
이미지 하나는 5MiB, 본문과 동반 첨부의 입력 합계는 10MiB를 상한으로 둔다.
localStorage 용량 초과는 별도로 처리한다. 저장 실패 때 화면의 입력을 보존하고 백업 내보내기를 제공한다.
한도를 넘는 첨부는 로컬 CLI로 가져오도록 안내한다.
Markdown 단독 내보내기는 상대경로를 유지한다. 내려받은 `.md`를 원래 첨부 폴더에 저장해야 한다.
JSON 백업은 함께 선택한 첨부와 업로드한 data URL을 보존한다. 공개 URL 참조만 있는 파일은 완전한 첨부 백업이라고 표시하지 않는다.
상대 첨부가 빠지면 누락 목록을 보여준다. 기존 본문을 지우거나 첨부 경로를 조용히 바꾸지 않는다.

로컬 가져오기는 허용한 이미지 MIME을 검증하고 해시 이름의 형제 파일로 추출한다.
공개 글에서 받은 `/content/assets/<원본 ID>/...`도 해당 ID의 로컬 첨부로 해석한다.
CLI는 전체 문서의 `./파일명`을 입력 Markdown 옆의 실제 파일에서 읽는다. 브라우저의 파일 접근과 구분한다.
첨부가 없으면 저장을 중단한다. 초기 버전에서 ZIP 내보내기와 임의 원격 다운로드를 추가하지 않는다.

## 8. 빌드와 배포

```text
content/ 정식 문서 + categories.json
    ↓ 파싱·관계 검증·상속 계산
전체 문서 객체
    ├── 공개 허용 필드 선택 → public/content/index.json
    │                       public/content/posts/<ID>.json
    │                       public/content/categories.json
    ├── 공개 첨부 복사     → public/content/assets/<ID>/...
    └── 후속 확장 계약    → 앱 밖의 지식 색인
```

`prepare-site.mjs`는 이전 JSON 입력을 Markdown 입력으로 바꾼다.
submodule이 없으면 오류로 중단한다. 남은 `posts.json`으로 자동 대체하지 않는다.
검증과 임시 출력 생성을 끝낸 뒤 기존 생성 디렉터리를 교체한다.
실패한 빌드는 기존 생성 결과와 정식 원본을 지우면 안 된다.
`npm run check:content`는 지정한 `CONTENT_ROOT`의 실제 글·관계·첨부를 검증하고 집계와 오류 수를 출력한다.
작은 임시 입력의 단위 검사만으로 실제 submodule 검사를 대신하지 않는다.
기존 corpus·목차 검사는 정식 Markdown의 공개 projection을 읽도록 바꾼다.

- Actions checkout은 기록한 submodule 커밋을 초기화한다. 빌드에서 원격 최신 브랜치를 추적하지 않는다.
- 앱 버전 정보에 `contentCommit`을 추가한다. 앱 커밋과 콘텐츠 커밋을 함께 기록한다.
- 배포용 Git 빌드는 콘텐츠 HEAD와 앱 gitlink가 같고 콘텐츠 작업 트리가 깨끗한지 확인한다.
- CLI 포장은 해당 커밋의 깨끗한 콘텐츠에서 만들고, 같은 절차에서 `CONTENT_COMMIT_SHA`를 빌드 입력으로 전달한다.
- Git 정보가 없는 업로드에서 콘텐츠 커밋을 확인할 수 없으면 오류로 중단한다.
- 앱 밖 staging을 `CONTENT_ROOT`로 검사하는 로컬 빌드는 허용한다. 이 경우 `contentCommit: null`로 표시하고 배포 입력으로 사용하지 않는다.
- `.vercelignore`는 콘텐츠 원본을 빌드 입력에 포함한다. 로컬 wiki와 수집 캐시는 제외한다.
- 콘텐츠 커밋을 먼저 원격에 올리고, 그 뒤 앱의 gitlink를 갱신한다.

공개 HTTPS submodule을 Vercel Git 연동에서 가져오는 방식은 공식 지원 범위다.
이 프로젝트의 새 연결과 CLI 포장은 실제 배포 전에 따로 검증해야 한다.
이 문서는 배포 실행이나 공개 범위 확대의 기록이 아니다.

## 9. 로컬 LLM wiki 확장

공개 콘텐츠는 근거 자료로 읽는다. AI가 만든 종합 문서는 앱 밖의 별도 로컬 경로에 둔다.
후속 wiki 폴더도 ID 기준으로 고정하고, 제목 Markdown과 첨부를 함께 둘 수 있다.

```text
second-brain-local/                       # 후속 로컬 시스템, 공개 저장소 밖
├── AGENTS.md
├── catalog.jsonl                         # ID·경로·요약·태그·revision 색인
├── index.md                              # 문서 진입점
├── wiki/
│   └── <wiki UUID>/
│       └── <개념 제목>.md
└── log.md                                # AI 작업·검토 기록
```

이번 리팩터링은 색인 레코드와 에이전트 작업 규칙을 문서로 확정한다. 생성 명령과 wiki 파일 순회는 구현하지 않는다.
후속 생성기는 자신이 만든 `catalog.jsonl`만 교체한다. `index.md`, `wiki/`, `log.md`와 개인 `AGENTS.md`는 덮어쓰지 않는다.
후속 출력 경로가 앱·콘텐츠·`public`·`dist` 안으로 해석되면 거부해야 한다.

- 원본 색인은 글 ID, 실제 파일 경로, 전체 메타데이터와 revision을 포함한다.
- 색인의 `path`는 콘텐츠 root 기준 상대경로다. 로컬 root는 실행 환경에서 정하고 공개 Git에 절대경로를 기록하지 않는다.
- AI는 색인으로 문서를 찾고 본문과 필요한 이미지를 읽는다. 요약만으로 원문 전체를 읽었다고 판단하지 않는다.
- wiki 문서의 `source_ids`는 근거 ID다. `source_revisions` 확장 필드로 사용한 revision을 기록한다.
- `source_revisions`는 글 ID→SHA-256 매핑이다. 해시는 소문자 16진수 64자로 표현한다.
- 후속 wiki 처리는 원본 revision이 달라지면 해당 문서를 재검토 대상으로 보고해야 한다.
- revision은 Markdown 바이트 기준이다. 이미지 바이트까지 근거로 사용하면 첨부 해시도 `source_assets` 확장 필드에 기록한다.
- `source_assets`는 글 ID→형제 파일명→SHA-256 매핑이다. 본문과 첨부의 변경을 구분한다.
- AI는 원본 내용을 자동 교정하거나 기술 주장을 사실로 확정하지 않는다.
- AI가 원본 메타데이터를 보강하면 변경 diff와 검토 상태를 남긴다. 본문 수정과 구분해 검토한다.
- 요약이 없는 글은 빈 값과 `unreviewed`를 유지한다. 마이그레이션에서 추측 요약을 채우지 않는다.

검색 서버와 자동 wiki 작성기는 만들지 않는다. 현재 문서 계약을 재사용해 필요할 때 색인 생성을 추가한다.
이는 원자료·파생 wiki·작업 규칙을 구분하는 LLM Wiki의 원칙을 적용한 설계다.

## 10. 이전과 복구

1. 구현 시작 시 작업 트리, 게시 데이터, 작성본, asset map과 파일 해시를 기록한다.
2. 최신 게시 데이터에 작성본을 ID로 합친다. 현재 공개 asset map을 적용한다.
3. 앱 밖의 staging 디렉터리에 전체 콘텐츠를 생성한다. 정식 입력을 직접 덮어쓰지 않는다.
4. 기존 계층·ID·날짜·분류와 본문을 비교한다. URL 재작성 외의 본문 변경을 금지한다.
5. 같은 입력을 다시 실행해 출력 해시가 같은지 검사한다.
6. 검증한 staging을 별도 콘텐츠 저장소의 첫 커밋으로 보관한다.
7. 원격 커밋 접근과 외부 백업을 확인한다. 앱의 기존 `content/` 추적을 해제한 뒤 같은 경로에 submodule을 연결한다.
8. 앱의 전환 후보를 커밋한다. 해당 앱 SHA를 새로 체크아웃하고 submodule 초기화·전체 검사·실데이터 검사·빌드를 실행한다.
9. 검증 뒤 옛 공개 첨부 사본을 정리하고 앱에 커밋한다. 정리한 최종 SHA에서도 새 체크아웃 검사를 반복한다.

이전 보고서는 기존 경로→새 ID, 파일 해시, 누락 참조, 외부 URL과 미소유 첨부를 포함한다.
카테고리 브라우저 개인 설정은 자동으로 원본 분류에 승격하지 않는다.
원문 Notion 속성과 사용하지 않는 수집 메타데이터는 공개 검토 후에만 확장 필드로 옮긴다.
캐시·과거 이력·전체 원본 백업은 공개 콘텐츠 저장소로 복사하지 않는다.
기존 수집·복구·변환 CLI는 전환 뒤 쓰기 시작 전에 중단하게 한다. 변환 함수의 검사는 유지한다.
새 staging CLI는 후속 작업이다. 이전 검사는 이전 전 백업 환경에서만 실행하고 새 앱의 기본 검사에서 분리한다.

삭제 전 앱 밖에 해시로 확인한 백업과 이전 보고서를 보존한다.
복구할 때는 앱 커밋과 콘텐츠 커밋을 함께 되돌린다. 서로 다른 세대의 입력과 빌드 코드를 섞지 않는다.

## 11. 검증과 완료 기준

다음 항목은 실행 단계의 완료 기준이다. 이 문서 작성 중에는 구현 검사와 빌드를 실행하지 않았다.

- C01: submodule을 포함한 새 체크아웃이 외부 원문 폴더 없이 빌드된다.
- C02: 기준 집계의 모든 글과 ID·부모 관계·날짜·분류를 보존한다. 빈 글도 포함한다.
- C03: 참조한 첨부의 누락이 없고 이전 바이트 해시가 기준과 같다. 미소유 파일은 보고서에 남는다.
- C04: 전체 문서·초안·백업 왕복에서 확장 메타데이터·정식 ID·선택한 첨부를 보존한다. 본문 미편집 왕복은 원문 바이트가 같다.
- C05: AI 전용 표식이 공개 JSON·목록·본문·편집기 DOM·공개 다운로드에 나타나지 않는다.
- C06: 일반 본문의 구분선은 유지한다. 잘못된 frontmatter가 본문에 노출되지 않는다.
- C07: 전체 편집본·공개 수정본의 충돌, 누락 첨부와 파싱 실패에서 원본과 이전 생성 결과를 보존한다.
- C08: 카테고리·부모 변경 전후에 원본 글 폴더와 첨부 파일 해시가 같다.
- C09: 첨부 링크를 글로 오인하지 않고 기존 글 주소와 fragment가 동작한다.
- C10: HTML·GFM·수식·코드의 현재 렌더링 회귀 검사를 통과한다.
- C11: wiki의 외부 저장 위치·색인 형식·근거 ID·revision 계약을 문서화한다. 공개 빌드는 로컬 지식 파일을 포함하지 않는다.
- C12: 연결된 Chrome에서 가져오기·자동 저장·미리보기·다운로드·실제 이미지 요청을 확인한다.

실제 처리 시간은 측정하지 않았다. 실행 단계에서 전체 준비 시간과 분류 변경 후 준비 시간을 따로 기록한다.
파일 이동이 없는 구조라는 이유로 재색인·검사·배포 비용까지 일정하다고 주장하지 않는다.
