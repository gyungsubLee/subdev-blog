# 노션형 편집기와 GitHub 이중 형식 저장 설계

사용자는 기존 노션형 글쓰기 UI를 사용한다. 저장하면 연결된 콘텐츠 저장소에 Markdown과 `editor.json`을 같은 커밋으로 기록한다.
2026-10-25에 사용자가 설계서 작성과 리팩터링을 함께 요청했다. 이 문서는 해당 요청의 구현 기준이다.

## 목표와 범위

- 새 글과 편집 원본이 있는 글은 기존 BlockNote 화면과 블록 기능을 사용한다.
- 본문 편집의 기준은 `editor.json`이다. 블로그는 함께 생성한 Markdown을 기존 공개 조회 경로로 읽는다.
- 기존 인증, CSRF, 요청 재시도, 첨부 업로드, GitHub 커밋 기능을 재사용한다.
- 런타임 의존성을 추가하지 않는다. 기존 Markdown을 일괄 변환하지 않는다.
- 실제 운영 글을 시험 목적으로 생성하거나 수정하지 않는다. 원격 푸시와 배포는 이 작업에 포함하지 않는다.

## 저장 계약

기존 `posts/<글 UUID>/<제목>.md`를 유지한다. 같은 폴더에 선택 파일 `editor.json`을 둔다.
Markdown의 YAML 메타데이터는 기존 계약을 유지한다. 편집 JSON은 제목과 분류를 중복 관리하지 않는다.

```json
{
  "schemaVersion": 1,
  "documentId": "12345678-1234-1234-1234-123456789abc",
  "markdownHash": "Markdown 본문 UTF-8 바이트의 SHA-256",
  "blocks": []
}
```

실제 `blocks`는 비어 있지 않은 BlockNote 블록 배열이다. 블록 종류, 속성, 인라인 내용과 하위 블록을 보존한다.
검증기는 버전, 글 ID, 해시와 블록 구조를 검사한다. 깊이와 개수에 상한을 둬 비정상 입력을 거부한다.
해시는 JSON과 현재 Markdown 본문의 연결을 확인한다. 블록을 Markdown으로 변환한 의미의 동일성은 변환기 검사로 검증한다.

`editor.json`은 예약 파일명이다. 일반 첨부의 업로드, 목록과 공개 첨부 처리에서 제외한다.
대소문자와 인코딩을 바꾼 예약 이름도 첨부로 받지 않는다. 공개 GitHub 저장소의 원본 공개 범위는 달라지지 않는다.

## 읽기와 충돌

인증한 원본 조회 응답에 `editor`와 `editorRevision`을 추가한다.
`editorRevision`은 편집 JSON 파일 바이트의 SHA-256이다. 파일이 없으면 `null`이다.
기존 Markdown `revision`의 의미는 유지한다. 저장 요청은 `baseCommit`, `baseRevision`, `baseEditorRevision`으로 충돌을 확인한다.

JSON의 해시와 본문이 다르면 블록 편집과 덮어쓰기를 중단한다. 사용자는 원문을 보존하거나 내보낼 수 있어야 한다.
지원하지 않는 JSON 버전이나 손상된 블록도 같은 정책을 적용한다. 실패한 초안을 자동 삭제하지 않는다.
인증한 읽기 응답은 이 경우 `editorError`와 보존 가능한 `editorRaw`를 제공한다. 화면은 저장을 막고 원문 내보내기를 제공한다.
저장과 후보 검증은 복구용 읽기를 사용하지 않는다. 손상된 원본을 정상 문서로 간주하지 않는다.
변경 없음 판정은 두 파일을 모두 비교한다. JSON 속성만 바뀌어도 저장할 수 있어야 한다.

## 저장 흐름

1. 편집기는 같은 시점의 블록 배열과 Markdown을 만든다.
2. 편집기는 본문 해시를 포함한 편집 JSON을 만든다.
3. 서버는 메타데이터, 두 파일의 연결, revision과 첨부를 검사한다.
4. 서버는 기존 Git tree 변경 목록에 Markdown과 JSON을 함께 넣는다.
5. 기존 커밋과 브랜치 갱신 흐름으로 두 파일을 원자적으로 반영한다.
6. 저장 결과의 콘텐츠 커밋을 기준으로 공개 화면을 다시 조회한다.

현재 공개 API는 콘텐츠 저장소를 직접 조회한다. 글 확인에 앱 재배포를 필수 조건으로 추가하지 않는다.
기존 후보 검증과 로컬 콘텐츠 검사에도 같은 파일 계약을 적용한다.

## 글쓰기 UI

새 글에는 기존 `editor-page`, 제목 입력, 슬래시 메뉴와 노트 블록 화면을 사용한다.
브라우저 자동 저장은 복구용 초안이다. 사용자가 누르는 저장 버튼은 GitHub 원본 저장을 요청한다.
기존 CMS의 정식 분류 선택, 오류 안내와 저장 결과를 연결한다.
첨부는 기존 업로드 경로를 사용한다. 저장된 블록과 Markdown에는 안정적인 형제 파일 경로를 사용한다.
기존의 `파일명`과 `./파일명` 참조를 모두 미리보기에서 해석한다. 연속 업로드와 백업 가져오기도 첨부 SHA를 보존한다.
`Cmd/Ctrl+S`는 브라우저의 페이지 저장을 열지 않는다. 기존 도움말대로 복구용 초안을 유지한다.

## 기존 Markdown 글

편집 JSON이 없는 글은 원문 Markdown 편집을 계속 지원한다.
사용자가 블록 편집 전환을 명시적으로 선택하면 변환 손실 가능성을 알리고 전환한다. 원문 내보내기를 제공한다.
제목이나 분류만 바꾸면 본문 바이트를 보존한다. 블록 전환을 선택하지 않은 글에는 JSON을 자동 생성하지 않는다.

## 블로그 표시

일반 문장은 Markdown으로 생성한다. 접기와 노트 블록은 허용한 HTML로 의미를 보존한다.
코드 캡션과 줄바꿈 설정은 필요한 속성을 명시적으로 전달한다. 블로그가 해당 속성을 해석하도록 맞춘다.
접기 제목도 접기 기능을 보존한다. 글자색, 배경색, 정렬과 밑줄은 고정 팔레트와 허용한 속성으로 표시한다.
HTML 정화는 유지한다. 기능을 복원하려고 임의의 스타일이나 실행 코드를 허용하지 않는다.
블록 데이터 복원과 공개 화면 표시를 각각 검사한다.

## 검증 기준

- 기존 UI의 슬래시 메뉴, 노트, 접기, 코드 설정을 확인한다.
- 두 파일 생성과 반복 수정이 하나의 Git 커밋으로 반영되는지 확인한다.
- 브라우저 초안 없이 다시 열어 블록 속성을 비교한다.
- 손상 JSON, 해시 불일치, 예약 첨부 이름과 오래된 revision을 거부하는지 확인한다.
- 기존 Markdown의 제목 수정, 첨부, 메타데이터 보존을 확인한다.
- 공개 API와 빌드가 편집 JSON을 일반 첨부로 내보내지 않는지 확인한다.
- 저장 실패와 재로그인 뒤 초안과 요청 ID를 보존하는지 확인한다.
- 적절한 개별 검사 후 전체 검사와 빌드를 실행한다. 브라우저 확인은 전용 Chrome 탭을 사용한다.
