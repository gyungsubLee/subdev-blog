# 캐시 우선 표시·디바운스 벌크 동기화

사용자가2026-11-04에 구현·실제 앱 E2E·전후 실측을 승인했다. 확정한 기준은 다음과 같다.

- 공개 목록과 방문한 본문, 관리 카테고리는 기기 캐시를 먼저 표시한다. 빈 캐시는 최초 조회가 필요하다.
- 입력은 기기에 보관한다. 저장·게시를 누른 변경만 낙관적으로 반영하고 원격 동기화를 예약한다. 초안을 자동 공개하지 않는다.
- 마지막 저장·게시 요청부터5초가 지나면 전송한다. 새 요청은 타이머를 다시 시작한다. 강제 최대 대기시간이나 주기적 재전송은 없다.
- 같은 문서의 미전송 수정은 최신본 하나로 합친다. 진행 중인 묶음은 고정하며 추가 수정은 다음 묶음으로 보관한다.
- 여러 글·카테고리를 한 요청으로 검증하고 원본 Git 커밋 하나로 반영한다. 개별 원격 저장을 묶음으로 포장하지 않는다.
- 전송 전에 요청 ID·payload·기준 버전을 IndexedDB에 보관한다. 인증 정보는 보관하지 않는다. 재실행과 재연결에서 요청을 복구한다.
- 통신·서버 오류는5초·15초·60초 간격으로 최대3회 재시도한다.401·403·409는 자동 반복하지 않는다. 같은 요청 ID와 payload를 유지한다.
- 원격 저장이 확인된 전송 데이터만 하루 한 번 정리한다. 요청 ID·내용 해시·커밋 확인이 필요하다. 실패·미확인·편집 중 데이터는 자동 삭제하지 않는다.
- 정리는 별도 Worker에서 실행한다. UI·전송과 병렬로 처리하며, IndexedDB 트랜잭션과 기한 있는 잠금으로 중복 실행을 막는다. 앱이 꺼져 있으면 다음 실행 때 재개한다.
- 전송 기록은 scope당 50MiB·미전송 대상100개·보관 묶음500개로 제한한다. 초과하면 신규 원격 저장을 접수하지 않으며 기존 편집을 덮어쓰거나 삭제하지 않는다. 같은 대상은 합쳐 누적을 줄인다.
- 한 묶음은 최대20작업·기존 HTTP 본문4MiB 한도다. 다음 묶음으로 나눠 처리한다. 필요한 새 카테고리 준비는 같은 묶음 안에서 처리한다.
- 화면 구성·색·문구·기존 초안·삭제 확인·세션·Origin·CSRF·저장 충돌을 보존한다. 기존 상태 UI로 원격 완료와 확인 중을 구분한다.
- 실제 사용자 콘텐츠 저장·삭제·커밋·푸시·배포는 하지 않는다. 쓰기·실패 주입은 폐기 가능한 fixture에서 검증한다. 실제 GitHub 조회·앱 읽기는 별도로 확인한다.

정확성 검사와 성능 측정을 구분한다. 기존 편집기 검사 실패와 공개 생성물의 다른 작업은 별도 기록한다. 기존 dirty 수정은 입력이며 다른 작업의 변경을 되돌리지 않는다.

원격 확인 기록은 기기에 적용하기 전에는 정리하지 않는다. 같은 대상의 확인 응답은 저장한 버전을 비교한다. 더 오래된 응답은 최신 원본과 공개 캐시를 덮어쓰지 않는다. 보관 기록 500개에서는 확인 기록을 추가할 공간이 생길 때까지 전송도 멈춘다.


## 2026-11-05 후속 승인

사용자가 원본 저장과 공개 생성을 분리하고 실제 GitHub에서 다시 측정하도록 승인했다. 기존 저장·게시 경계와 5초 정책을 유지한다.

기기 저장을 완료한 뒤 화면에 반영한다. 백그라운드 원본 저장의 유효 receipt는 `saved`로 확인한다. 공개 JSON은 기존 content push workflow만 생성한다. workflow는 생성물을 검증한 뒤 `public-ready/main` 원본 참조를 전진시킨다. 기본 reader는 이 참조의 정상 공개본을 읽는다. 이전 workflow는 Git의 fast-forward 검사를 우회하지 않는다.

원본 확인 기록은 해당 공개본을 화면에 적용할 때까지 유지한다. 변경 없음 요청도 공개 준비를 추적한다. 원본 commit과 공개 commit을 구분한다. 기존 캐시·재시도·충돌·복구·정리 한도는 유지한다. 실제 검증에는 고유한 임시 글 하나만 사용하고 마지막에 삭제한다. 모든 기존 원본 파일의 SHA가 같아야 정리를 완료한다.

[실행 계획](../plans/2026-11-05-optimistic-workflow.md)과 [실측 보고서](../../research/2026-11-05-optimistic-workflow/README.md)를 후속 결과로 삼는다. 전체 React 편집기의 화면 지연과 실제 브라우저 대용량 메모리는 이번 작은 글 측정으로 검증했다고 판단하지 않는다.


## 2026-11-05 단일 GitHub mutation 후속 승인

사용자가 일반 저장의 GitHub 호출을 한 번으로 바꾸고 실제 요청 수와 시간을 다시 측정하도록 승인했다. 준비된 원본의 변경은 `createCommitOnBranch`와 `expectedHeadOid`로 한 번에 저장한다. 기존 5초 정책과 공개 workflow는 유지한다.

새 atomic 요청은 `atomic-<UUID>` 식별자를 사용한다. 같은 커밋에 `.cms/requests/<requestId>.json` 확인 파일을 기록한다. 기존 UUID 요청과 대기 기록은 기존 방식으로 복구한다. 기기에 보관한 전송 기록이 있으면 payload를 바꾸지 않고 읽기 복구를 먼저 요청한다. 요청 ID·내용 해시·기준 commit과 정확히 한 부모를 확인한다.

처음 원본이 없거나 캐시가 비었으면 준비 조회가 필요하다. 읽기 복구와 큰 첨부 참조의 기존 SHA 경로에도 추가 호출이 필요하다. 이 호출을 숨겨 모든 경로가 한 번이라고 보고하지 않는다. 기존 파일 SHA를 보존하고 새 확인 파일은 복구 이력으로 유지한다. [후속 계획](../plans/2026-11-05-single-request-save.md)과 [새 실측](../../research/2026-11-05-single-request/README.md)을 결과로 삼는다.
