# GitHub 인증과 콘텐츠 관리 설계

2026-10-24 KST에 작성했다. 사용자는 공개 조회와 본인만 가능한 생성·수정·삭제를 확정했다.
이 문서는 구현 전 검토본이다. 인증, 원본 저장과 게시의 세부 계약을 정한다.

## 1. 목표와 범위

누구나 로그인 없이 정식 글과 카테고리를 조회한다.
본인은 GitHub 로그인과 저장소 연결 확인을 통과한 뒤 Post와 Category를 생성·수정·삭제한다.
저장한 변경은 콘텐츠 저장소에 커밋한다. 앱의 서브모듈 참조 갱신과 배포도 자동화한다.

다음 순서로 구현한다. 각 단계는 같은 목표를 향하는 독립 검증 단위다.

1. GitHub 로그인, 저장소 연결 확인과 서버 권한 검사를 구현한다.
2. Post와 Category의 원본 편집 및 저장 요청을 연결한다.
3. Actions에서 전체 검증, 원본 브랜치 갱신과 배포를 연결한다.

조회 경로는 인증 API의 성공을 기다리지 않는다. 인증 장애가 공개 조회를 막아서는 안 된다.
다중 작성자, 임의 저장소 선택, 자동 AI 실행과 별도 데이터베이스는 범위에 넣지 않는다.

## 2. 현재 코드에서 확인한 경계

- `src/app/usePosts.ts`는 빌드가 만든 공개 JSON을 읽는다.
- `useDraftEditor.ts`와 `useCategoryCatalog.ts`의 저장 대상은 현재 `localStorage`다.
- `scripts/content.mjs`의 `validateContent`는 정식 문서·계층·분류·참조·첨부를 검사한다.
- `readContent`와 `writeContentDocument`는 로컬 파일시스템을 사용한다.
- `src/shared/document.mjs`의 `mergeDocumentPatch`는 원본 메타데이터를 보존하며 수정본을 합친다.
- 기존 BlockNote 편집기는 `blocksToMarkdownLossy`로 본문을 변환한다. 이 결과로 기존 원본을 무조건 덮어쓰면 안 된다.
- 현재 Actions 빌드는 태그 푸시와 수동 실행을 받는다. 콘텐츠 저장과 배포를 연결한 경로는 없다.

## 3. 저장소와 인증 주체

콘텐츠 저장소는 `gyungsubLee/subdev-blog-content`로 고정한다.
앱 저장소는 `gyungsubLee/subdev-blog`로 고정한다. 요청 본문으로 저장소나 브랜치를 바꿀 수 없다.
배포 설정은 두 저장소의 숫자 ID, 허용할 사용자 ID와 대상 브랜치를 보관한다.
표시용 계정명만으로 본인을 판별하지 않는다. 처음 로그인한 계정을 자동 관리자로 등록하지도 않는다.

GitHub App 하나를 만들고 두 저장소만 선택해 설치한다.
App 권한은 `Contents: write`, `Actions: write`와 기본 `Metadata: read`로 한정한다.
런타임에는 `Administration`, `Workflows`, 이메일과 조직 전체 접근 권한을 요청하지 않는다.
App 등록과 저장소 설치는 사용자 계정의 초기 설정 단계에서 수행한다.

GitHub 로그인과 App 설치는 다른 검사다. 공개 저장소 읽기 성공만으로 쓰기 준비가 끝났다고 표시하지 않는다.
Vercel API는 본인의 GitHub App 사용자 토큰으로 변경 요청과 workflow 실행을 요청한다.
Actions는 App 설치 토큰으로 자동 작업을 수행한다. App 개인 키는 Actions secrets에만 둔다.

## 4. 로그인과 세션

서버 API는 Vercel Functions로 제공한다. 공개 React 앱에 GitHub 비밀값을 포함하지 않는다.
OAuth authorization-code 흐름에 임의 `state`와 PKCE `S256`을 사용한다.
콜백 주소와 돌아갈 경로는 서버가 허용한 값만 사용한다.

서버는 `GET /user` 결과의 숫자 ID를 허용한 사용자 ID와 대조한다.
다른 계정이면 관리 세션을 발급하지 않는다. 기존 초안은 그대로 보존한다.
사용자 토큰은 서버 키로 암호화하고 변조를 검사하는 HttpOnly 쿠키에 넣는다.
운영 쿠키는 `__Host-` 접두사, `Secure`, `SameSite=Lax`, `Path=/`를 사용한다.
세션 수명은 최대 1시간이며 GitHub 토큰 만료 시각보다 짧아야 한다.
처음에는 refresh token을 보관하지 않는다. 만료하면 다시 로그인한다.

세션 상태 응답에는 사용자 표시명과 연결 상태만 보낸다. GitHub 토큰을 응답 JSON이나 로그에 넣지 않는다.
변경 요청마다 세션, 본인 ID, Origin과 CSRF 토큰을 검사한다.
로그아웃은 세션 쿠키를 삭제한다. 로그인 상태는 브라우저 JavaScript의 저장값만으로 결정하지 않는다.

초기 API 경계는 다음과 같다.

- `GET /api/auth/github`: 로그인 시작.
- `GET /api/auth/callback`: 코드 교환과 본인 확인.
- `GET /api/session`: 로그인 상태와 저장소 연결 상태 조회.
- `POST /api/logout`: 세션 삭제.

## 5. 저장소 연결 확인과 편집 허용

로그인 뒤 서버는 다음 조건을 확인한다.

- App 설치가 중지되지 않았고 두 저장소의 숫자 ID가 설치 범위에 있다.
- 본인과 App의 권한 범위가 모두 요청한 작업을 허용한다.
- 저장소가 보관 또는 사용 중지 상태가 아니며 대상 브랜치가 존재한다.
- 앱의 `content` gitlink와 `.gitmodules`가 고정한 콘텐츠 저장소를 가리킨다.
- `categories.json`, `posts/`와 정식 스키마를 읽을 수 있다.
- 게시 workflow가 대상 앱 브랜치에서 활성 상태다.

원본 브랜치가 앱에 배포된 콘텐츠 커밋보다 앞서 있으면 그 차이를 표시한다.
관리 편집기는 원본 브랜치에서 받은 문서를 사용한다. 오래된 공개 JSON을 수정 기준으로 삼지 않는다.
브랜치 규칙을 읽을 수 있어도 실제 쓰기 성공을 보장하지는 않는다.
연결 확인은 원본을 바꾸는 시험 커밋을 만들지 않는다.

클라이언트 상태는 `signed_out`, `checking`, `ready`, `blocked`로 구분한다.
`ready`에서만 글쓰기, 수정, 삭제와 카테고리 저장을 허용한다.
비로그인 사용자는 같은 경로의 글과 카테고리를 읽을 수 있다.
서버도 모든 변경 요청에서 같은 조건을 검사한다. 버튼 숨김만으로 권한을 구현하지 않는다.
화면은 연결한 저장소와 브랜치를 표시한다. 실패하면 원인과 재로그인 또는 연결 재확인 동작을 제공한다.

## 6. 정식 Post의 생성·수정·삭제

정식 글 편집은 원본 Markdown과 원본 revision을 인증 API에서 받는다.
기존 글의 기본 편집 모드는 원문 Markdown이다. 변환한 공개 본문을 저장 입력으로 재사용하지 않는다.
기존 블록 초안은 보존한다. 정식 원본을 BlockNote로 자동 왕복 변환하지 않는다.
제목이나 분류만 바꾸면 본문 바이트를 보존한다.
본문을 바꾸면 작성한 Markdown을 저장한다. 지원하지 않는 블록을 자동 변환하거나 삭제하지 않는다.

서버는 기존 원본을 읽고 허용한 변경 필드만 합친다.
`mergeDocumentPatch`의 revision 검사와 메타데이터 보존 규칙을 재사용한다.
`notionProperties`, 별칭과 알려지지 않은 확장 필드도 보존한다.
본문 변경은 `review_status: needs_review`로 표시한다. 실제 변경이 없으면 새 게시 커밋을 만들지 않는다.

새 글은 UUID와 정식 기본 메타데이터를 발급한다. 파일명은 기존 `canonicalFilename` 규칙을 사용한다.
제목 변경은 같은 UUID 폴더 안에서 Markdown 파일만 바꾼다.
첨부는 기존 경로·이름·바이트를 보존한다. 새 첨부의 경로 이탈과 이름 충돌을 거부한다.
첨부 요청의 HTTP 본문 전체는 4MiB 이하로 제한한다. 큰 파일은 나눠 업로드하고 workflow 입력에 담지 않는다.
첨부 업로드는 Git blob만 만든다. 저장 요청이 확정되기 전에는 원본 브랜치를 바꾸지 않는다.

초기 삭제는 참조가 없는 말단 글에 한정한다.
하위 글, `related_ids`, `source_ids`, 내부 Markdown 링크가 있으면 삭제를 거부하고 의존하는 글을 알려준다.
검사는 삭제 전 링크 해석 결과도 사용한다. Notion 링크가 삭제 뒤 외부 링크로 바뀌어 검사를 피하면 안 된다.
하위 글이나 참조를 자동으로 지우지 않는다. 삭제 가능한 글은 UUID 폴더와 첨부를 같은 커밋에서 제거한다.

## 7. 정식 Category의 생성·수정·삭제

정식 카테고리 관리는 원본 `categories.json`과 그 revision을 사용한다.
브라우저의 개인 분류 설정을 정식 카테고리로 업로드하지 않는다.
기존 `localStorage` 값은 보존하되 정식 관리 화면의 원본과 합치지 않는다.
정식 카테고리의 이름·계층·순서는 배포한 원본을 기준으로 표시한다.

생성 시 안정된 ID를 발급한다. 이름 변경, 부모 이동과 순서 변경 뒤에도 ID와 `sources`를 유지한다.
정식 계약이 허용하는 같은 표시명을 개인 설정의 중복 이름 규칙으로 거부하지 않는다.
변경할 때 ID 중복, 순환, 없는 부모와 중복 `sources`를 검사한다.
카테고리 레코드의 알려지지 않은 필드도 보존한다.
카테고리 변경 때문에 글 폴더나 첨부를 이동하지 않는다.

초기 삭제는 하위 카테고리와 직접 배정한 글이 없는 항목에 한정한다.
사용 중인 카테고리는 의존하는 항목을 먼저 이동한 뒤 삭제한다.
`group:unclassified`는 삭제할 수 없다. 하위 항목을 자동 삭제하거나 글을 몰래 재분류하지 않는다.

## 8. 검증 뒤 원본 브랜치에 적용

전체 원본을 매 Vercel 요청마다 복제하고 검사하지 않는다.
API는 GitHub Git 데이터 API로 바뀐 파일만 후보 커밋에 담는다.
후보는 콘텐츠 저장소의 `cms/requests/<UUID>` 브랜치에 둔다. 별도 작업 큐나 데이터베이스는 만들지 않는다.
후보의 부모는 저장 요청이 확인한 원본 브랜치 HEAD다.
같은 요청 ID를 재전송하면 기존 후보와 작업을 조회한다. 다른 바이트로 같은 요청 ID를 재사용하면 거부한다.

API는 고정한 앱 workflow에 요청 ID, 후보 SHA와 기준 SHA만 보낸다.
GitHub API 버전은 `2026-03-10`으로 고정한다.
Dispatch 응답의 `workflow_run_id`를 저장 상태 조회에 사용한다.
Workflow의 `run-name`은 `cms:<요청 UUID>:<후보 SHA>`로 고정한다.
응답을 잃으면 고정 workflow의 실행 목록에서 같은 `display_title`을 찾아 실행 ID를 복구한다.
응답을 받지 못한 요청은 후보와 기존 실행을 확인한 뒤 재시도한다. 중복 실행도 같은 후보만 처리해야 한다.

Actions는 신뢰한 앱 코드를 checkout한다. 후보 콘텐츠의 스크립트나 workflow를 실행하지 않는다.
허용한 `categories.json`과 `posts/<UUID>/` 밖의 변경은 거부한다.
후보의 부모, 원본 revision과 전체 스키마·계층·참조·첨부를 검사한다.
기존 `readContent`, `validateContent`, 문서 파서와 직렬화 규칙을 재사용한다.
원본 검사를 통과한 후보만 원본 브랜치에 fast-forward로 적용한다.
원본 HEAD가 기준 SHA면 후보를 적용한다. 이미 후보 SHA면 원본 저장을 반복하지 않고 게시를 재개한다.
원본 HEAD가 후보의 후속 커밋이면 더 새 변경에 포함된 요청으로 표시한다. 이전 후보로 게시를 되돌리지 않는다.
그 밖의 HEAD 변경은 충돌로 끝낸다. 강제 푸시로 다른 변경을 덮어쓰지 않는다.
이 검증 뒤의 후보 커밋이 정식 원본 변경 커밋이 된다.

변경 요청을 `cancel-in-progress`로 취소하지 않는다.
병렬 요청의 정합성은 기준 SHA와 fast-forward 조건으로 보장한다. 충돌한 요청의 초안은 남긴다.

## 9. 앱 참조 갱신과 배포

콘텐츠 원본을 적용한 뒤 앱의 `content` gitlink만 새 SHA로 갱신한 커밋을 만든다.
이 앱 커밋의 검사·빌드를 통과한 뒤 앱 브랜치에 적용한다.
앱 코드의 동시 변경을 덮어쓰지 않는다. 앱 브랜치가 바뀌면 새 기준에서 참조 갱신과 빌드를 다시 검사한다.
현재 앱 gitlink가 후보와 같으면 같은 참조 커밋을 다시 만들지 않는다.
현재 앱 gitlink가 후보의 후속 커밋이면 그 요청의 게시를 끝낸다. 예전 SHA로 되돌리는 커밋을 만들지 않는다.
앱 브랜치를 갱신하기 직전에 원본 HEAD와 현재 gitlink의 계보를 다시 검사한다. 갱신은 fast-forward만 허용한다.
콘텐츠와 앱은 별도 저장소이므로 두 커밋을 원자적으로 적용할 수 없다.
콘텐츠 저장 뒤 앱 갱신이 실패하면 `원본 저장 완료 · 게시 대기`로 표시한다.
재시도는 이미 저장한 콘텐츠 SHA를 사용한다. 같은 변경의 원본 커밋을 다시 만들지 않는다.

배포는 기존 Vercel 프로젝트를 사용한다. 처음에는 preview를 만들고 URL과 정확한 앱·콘텐츠 SHA를 검증한다.
운영 배포 전환은 검증한 결과를 사용자에게 보여준 뒤 별도로 승인받는다.
Git 없는 배포 입력은 기존 `CONTENT_COMMIT_SHA` 계약을 지킨다.
완료 검사는 실제 배포의 `build-info.json`과 공개 글·분류에서 두 SHA와 변경 내용을 확인한다.
더 새 배포에 포함된 요청은 요청 SHA가 배포 콘텐츠 SHA의 조상인지 확인한다.
GitHub 기본 토큰의 push가 다음 Actions를 실행한다고 가정하지 않는다. 필요한 작업은 명시적으로 이어 실행한다.

## 10. 화면 상태와 실패 처리

자동 저장은 브라우저 초안만 저장한다. 저장 또는 삭제를 확정할 때 게시 요청 하나를 만든다.
진행 상태는 `검증 중`, `원본 저장 완료`, `게시 대기`, `게시 완료`, `실패`로 구분한다.
후보 브랜치 생성이나 dispatch 성공을 원본 저장 성공으로 표시하지 않는다.
저장소 커밋 링크와 Actions 실행 링크는 검증한 응답 값으로 제공한다.

인증이 만료되면 `401`, 권한이 없으면 `403`, 원본 버전이 다르면 `409`를 반환한다.
잘못된 문서나 의존하는 항목 때문에 거부하면 `422`와 수정할 항목을 보낸다.
연결 실패와 제한 초과를 빈 목록이나 저장 성공으로 바꾸지 않는다.
실패하거나 결과를 확인하지 못하면 초안과 요청 ID를 보존한다.
삭제는 대상 제목과 의존 관계를 보여준 뒤 명시적으로 확정한다.

## 11. 검증 기준

- 비로그인 상태에서 글 목록·본문·카테고리 조회가 성공한다. 인증 서버 장애 때도 같은 결과여야 한다.
- 비로그인, 다른 계정, 변조한 세션, 만료한 토큰과 잘못된 Origin의 변경 요청이 원본을 바꾸지 않는다.
- 로그인만 성공하고 저장소 설치·쓰기 권한이 없으면 편집을 허용하지 않는다.
- 제목만 바꾼 글은 본문 바이트와 확장 메타데이터를 보존한다.
- 본문 수정, 첨부 추가, 새 글과 카테고리 변경이 각각 검증 뒤 원본 커밋에 들어간다.
- 오래된 revision과 병렬 요청이 다른 글이나 카테고리 변경을 덮어쓰지 않는다.
- 의존하는 글과 카테고리 삭제를 거부한다. 참조가 없는 항목은 원본에서 삭제한다.
- 변조한 후보 경로와 실패한 검증이 원본 브랜치를 바꾸지 않는다.
- 앱 갱신 또는 배포 실패 뒤 같은 요청을 재시도해도 원본 커밋이 중복되지 않는다.
- 두 요청의 실행 순서가 뒤바뀌어도 앱 gitlink나 배포가 이전 콘텐츠로 되돌아가지 않는다.
- Dispatch 응답을 잃어도 고정한 실행 이름으로 상태를 복구한다.
- 실제 로그인, 연결 확인, CUD와 공개 조회를 연결한 Chrome에서 확인한다. GitHub App 없는 대체 인증으로 통과를 주장하지 않는다.

처음에는 기존 Node test runner와 jsdom을 사용한다. 새로운 테스트 프레임워크나 런타임 의존성을 기본으로 추가하지 않는다.
실제 GitHub·Vercel 검사는 전용 preview와 검증용 콘텐츠에서 수행한다.
로컬 검사 통과, GitHub 원본 저장, Actions 성공과 실제 배포 확인을 각각 보고한다.

## 12. 초기 설정과 외부 경계

서버 설정은 GitHub App client ID·secret, 세션 암호화 키, 허용한 사용자 ID와 두 저장소의 ID·브랜치를 포함한다.
App 설치 ID와 정확한 callback origin도 고정한다. 설정이 없으면 공개 조회는 유지하고 관리는 차단한다.
Actions secrets에는 App ID·개인 키와 Vercel 배포 자격 증명을 둔다.
실제 비밀값은 문서, 프런트엔드 번들, 공개 로그와 저장소에 기록하지 않는다.
설정 예시와 설치 절차는 구현 단계에서 `.env.example`과 README에 추가한다.
App 등록, 설치, secrets 입력과 원격 workflow 실행 전에는 검토할 코드와 필요한 권한을 먼저 제시한다.
